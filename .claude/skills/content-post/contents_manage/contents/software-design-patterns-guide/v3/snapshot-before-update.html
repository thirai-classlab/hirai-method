ソフトウェアアーキテクチャ／設計パターンを 目的 → 構造 → メリデメ → たとえ話 → 実コード の統一フォーマットで網羅した完全ガイド。

はじめに ― なぜ「設計パターン」を知るべきか

家を建てる前に「2 階建てか平屋か」「鉄筋か木造か」を決めるように、ソフトウェアも どう組み立てるか を最初に決める必要がある。これが「アーキテクチャ／設計パターン」。

正しいパターンを選べないと、後から「機能追加のたびに別の場所が壊れる」「担当者が変わると誰も触れない」「一部だけ高速化したいのに全体を作り直す」といった事故が起きる。

1. レイヤ系アーキテクチャ

1.1 Layered Architecture

目的と使いどころ

ソフトウェアを 役割の違うレイヤに分離 し、上位レイヤが下位レイヤだけに依存するようにする最も基本のパターン。Eric Evans の DDD で広く知られる現代的な構成は次の 4 層:

  • プレゼンテーション層 — UI / API エンドポイント

  • アプリケーション層 — ユースケース／業務フロー調整

  • ドメイン層 — ビジネスルール・エンティティ

  • インフラ層 — DB / メール / 外部 API などの実装

中規模以上の業務システム、長期保守を前提とした SaaS、ドメインが明確で複雑な業務アプリで採用される。

古典的な 3 層 N-Tier（Presentation / Business / Data Access）は本パターンの簡略版にあたる。現代のレイヤ化は DDD 由来の 4 層構成が標準。

構造イメージ

メリット / デメリット

メリット

  • 役割が明確で新人にも説明しやすい

  • 上位の変更が下位に波及しにくい

  • フレームワーク非依存（Rails でも Spring でも適用可）

デメリット

  • レイヤを貫通する変更（新項目追加など）はファイル数が増える

  • 安易に「ドメイン層」が空っぽになり、貧血ドメインモデルになりやすい

日常のたとえ

社員食堂 をイメージしてほしい。

  1. お客さん（プレゼンテーション） がメニューを見て注文する

  2. 配膳カウンター（アプリケーション） が注文を受けて調理場に伝える

  3. キッチン（ドメイン） が「うちのレシピ」に従って料理を作る

  4. 食材庫（インフラ） が食材という外部資源を提供する

お客さんが直接食材庫に入ることはない。上から下へだけ 通る。

コード例（TypeScript）

// === ドメイン層 ===
class Order {
  constructor(public readonly id: string, public readonly total: number) {}
  applyDiscount(rate: number) {
    return new Order(this.id, this.total * (1 - rate));
  }
}

interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

// === アプリケーション層 ===
class ApplyDiscountUseCase {
  constructor(private readonly repo: OrderRepository) {}
  async run(orderId: string, rate: number) {
    const order = await this.repo.findById(orderId);
    if (!order) throw new Error("order not found");
    const updated = order.applyDiscount(rate);
    await this.repo.save(updated);
    return updated;
  }
}

// === インフラ層 ===
class PrismaOrderRepository implements OrderRepository {
  async findById(id: string) { return null; }
  async save(order: Order)   { /* prisma upsert */ }
}

// === プレゼンテーション層 ===
export async function POST(req: Request) {
  const { orderId, rate } = await req.json();
  const usecase = new ApplyDiscountUseCase(new PrismaOrderRepository());
  return Response.json(await usecase.run(orderId, rate));
}

1.2 Clean Architecture

目的と使いどころ

Robert C. Martin (Uncle Bob) 提唱。同心円状にレイヤを配置し、依存方向を常に内向き に制約する。中心は「ビジネスのルール」、外周は「フレームワーク / DB / UI」などの取り替え可能な詳細。

DB やフレームワークを後から差し替えたい長寿命プロダクト、ユニットテストを徹底したいエンタープライズ向けに最適。

構造イメージ

メリット / デメリット

メリット

  • DB を立ち上げずにビジネスロジックを単体テストできる

  • フレームワーク／インフラを後から差し替え可能

  • 長寿命のドメイン中心システムに強い

デメリット

  • ボイラープレート（インターフェース定義など）が増える

  • 小規模アプリだとオーバーキル

日常のたとえ

マトリョーシカ人形。

  • 中心（Entity）: 一番小さな人形 ＝ 一番変わらないビジネスルール

  • その外（Use Case）: 業務フローのルール

  • さらに外（Adapter）: 画面・API・DB との変換役

  • 一番外（Framework）: Web フレームワーク・ORM・外部 SaaS

外側の人形を取り替えても、中の人形は無事。

コード例（TypeScript）

// === Entity (中心) ===
class User {
  constructor(public readonly id: string, public readonly email: string) {}
}

// === Use Case ===
interface UserRepo {
  find(id: string): Promise<User | null>;
}
class GetUserUseCase {
  constructor(private readonly repo: UserRepo) {}
  async run(id: string): Promise<User> {
    const user = await this.repo.find(id);
    if (!user) throw new Error("not found");
    return user;
  }
}

// === Adapter ===
class SqlUserRepo implements UserRepo {
  async find(id: string) { return null; }
}

// === Framework (最外) ===
export async function GET(req: Request) {
  const usecase = new GetUserUseCase(new SqlUserRepo());
  const user = await usecase.run(new URL(req.url).searchParams.get("id") ?? "");
  return Response.json(user);
}

1.3 Hexagonal Architecture (Ports & Adapters)

目的と使いどころ

Alistair Cockburn 提唱。アプリケーションコアに 「ポート（差込口）」 を用意し、外界との接続を 「アダプター」 に分離する。何を繋いでも本体が動くように設計する。

外部サービス（決済、メール、外部 API）が多く、将来差し替えたいシステムや、テストで本物の依存を使いたくないケースに最適。

構造イメージ

メリット / デメリット

メリット

  • テストもただの Adapter にできる（本物の DB 不要）

  • インフラ差し替えが容易（MySQL → PostgreSQL、Stripe → 別決済）

デメリット

  • ポート／アダプタ定義が冗長に感じやすい

日常のたとえ

家電のコンセントとプラグ。本体（テレビ）は「電源が来る」ことしか知らない。海外用変換プラグを繋げば海外でも動く。

コード例（TypeScript）

// === Port ===
interface NotificationPort {
  send(message: string): Promise<void>;
}

// === Application Core ===
class OrderService {
  constructor(private readonly notifier: NotificationPort) {}
  async placeOrder(orderId: string) {
    await this.notifier.send(`注文 ${orderId} を受け付けました`);
  }
}

// === Adapter ===
class SlackAdapter implements NotificationPort {
  async send(msg: string) { /* Slack API */ }
}
class EmailAdapter implements NotificationPort {
  async send(msg: string) { /* SMTP */ }
}

new OrderService(new SlackAdapter()).placeOrder("o-1");

1.4 Onion Architecture

目的と使いどころ

Jeffrey Palermo 提唱。Clean Architecture の前身にあたり、同心円の中心にドメインモデル を置き、外側ほど可変な要素を配置する。

「外側は変わりやすく、内側は変わらない」 という設計哲学を全員で共有したい開発チーム向け。

構造イメージ

メリット / デメリット

メリット

  • ドメインモデルが他のレイヤに依存しないので純粋に保てる

  • DI コンテナとの相性が良い

デメリット

  • Clean Architecture とほぼ同じ思想で違いが分かりにくい

  • 「Application Service」と「Domain Service」の使い分けで議論になりやすい

日常のたとえ

地球の断面。中心の核は鉄とニッケルで何があっても変わらない。マントル → 地殻 → 大気と外側になるほど変化が激しい。

コード例（TypeScript）

// === Domain Model (核) ===
class Money {
  constructor(public readonly amount: number, public readonly currency: "JPY") {}
}

// === Domain Service ===
class TaxService {
  apply(price: Money): Money {
    return new Money(Math.floor(price.amount * 1.1), "JPY");
  }
}

// === Application Service ===
class CheckoutService {
  constructor(private readonly tax: TaxService) {}
  checkout(price: Money) { return this.tax.apply(price); }
}

2. プレゼンテーション系パターン

2.1 MVC (Model-View-Controller)

目的と使いどころ

UI に関する責務を データ (Model)・表示 (View)・制御 (Controller) の三役に分離する古典的パターン。Rails / Spring MVC / Laravel など Web フレームワーク全般で採用。

サーバーサイド Web アプリの基本構成として今も最もよく使われる。

構造イメージ

メリット / デメリット

メリット

  • 多くの Web フレームワークが標準対応

  • 役割分担が単純で学習しやすい

デメリット

  • View が肥大化して「Massive View Controller」化しやすい

  • 大規模化で責任の境界が曖昧になりやすい

日常のたとえ

レストラン。

  • モデル（キッチン）: 食材を扱い、料理を作る

  • ビュー（ホール）: お客さんに見える部分

  • コントローラー（店長）: 注文を受け、誰に何を頼むか判断する

コード例（TypeScript）

class TodoModel {
  private items: string[] = [];
  add(s: string) { this.items.push(s); }
  list() { return [...this.items]; }
}

class TodoView {
  render(items: string[]) {
    return items.map((s) => `<li>${s}</li>`).join("");
  }
}

class TodoController {
  constructor(private model: TodoModel, private view: TodoView) {}
  handleAdd(text: string) {
    this.model.add(text);
    return this.view.render(this.model.list());
  }
}

2.2 MVP (Model-View-Presenter)

目的と使いどころ

View を 完全に受け身（パッシブ） にし、すべての判断を Presenter が引き受ける。View にロジックを書かないので テストしやすい。

旧 Android、WinForms、GWT などで多用。View の単体テストがしづらいプラットフォームに向く。

構造イメージ

メリット / デメリット

メリット

  • View がパッシブなのでテストしやすい

  • ロジックが Presenter に集中する

デメリット

  • View と Presenter のインターフェースが多くなる

  • MVVM の登場でモバイル領域では下火

日常のたとえ

漫才の司会者。舞台上の芸人（View）は指示通り動くだけ。司会者（Presenter）が「次に何のネタを誰がやるか」をすべて決める。

コード例（TypeScript）

interface TodoView {
  showItems(items: string[]): void;
  showError(msg: string): void;
}

class TodoPresenter {
  private items: string[] = [];
  constructor(private view: TodoView) {}
  add(text: string) {
    if (!text) return this.view.showError("空文字は不可");
    this.items.push(text);
    this.view.showItems(this.items);
  }
}

2.3 MVVM (Model-View-ViewModel)

目的と使いどころ

View と ViewModel を データバインディング で結ぶ。View の状態は ViewModel に保持され、片方が変わるともう片方が自動で更新される。

WPF（Windows）, SwiftUI（iOS）, Vue.js などの 宣言的 UI フレームワーク と相性◎。

構造イメージ

メリット / デメリット

メリット

  • ボイラープレートが少なく宣言的に書ける

  • ViewModel が UI 状態を集約してテストしやすい

デメリット

  • バインディングのデバッグが難しいことがある

  • 大規模になると ViewModel が肥大化

日常のたとえ

鏡。あなた（Model）が手を上げれば、鏡像（View）も同じ動きをする。間にある鏡（ViewModel）が自動で反映を担う。

コード例（TypeScript）

import { signal } from "@preact/signals-core";

class TodoViewModel {
  items = signal<string[]>([]);
  add = (text: string) => {
    this.items.value = [...this.items.value, text];
  };
}

2.4 MVI (Model-View-Intent)

目的と使いどころ

ユーザー操作を 「意図（Intent）」 として表現し、Reducer で State を生成、View はその State を映すだけ、という 単方向データフロー のパターン。

リアクティブ／関数型志向のモバイル UI（Jetpack Compose, Cycle.js 等）で採用。

構造イメージ

メリット / デメリット

メリット

  • 状態遷移が予測可能でデバッグしやすい

  • Time-travel デバッガなどと相性◎

デメリット

  • イベント数が増えるとボイラープレートが多くなる

日常のたとえ

自動販売機。ボタンを押す（Intent）→ 内部状態が更新（State）→ 商品落下と表示（View）。同じボタンを押せば必ず同じ反応が返る。

コード例（TypeScript）

type Intent =
  | { type: "add"; text: string }
  | { type: "remove"; index: number };

type State = { items: string[] };

const reducer = (state: State, intent: Intent): State => {
  switch (intent.type) {
    case "add":    return { items: [...state.items, intent.text] };
    case "remove": return { items: state.items.filter((_, i) => i !== intent.index) };
  }
};

2.5 Flux / Redux

目的と使いどころ

Action → Reducer → Store → View の一方通行で状態を管理する Web 向けパターン。MVI と思想は同じ。

複数コンポーネントで状態を共有する React アプリで、デバッグ可能性と予測可能性を重視するときに採用。

構造イメージ

メリット / デメリット

メリット

  • 状態変更が 1 箇所（Reducer）に集約され、追跡しやすい

  • DevTools で操作履歴を遡れる

デメリット

  • 小規模だと冗長になりがち

  • ボイラープレートが多い（Redux Toolkit で緩和）

日常のたとえ

銀行 ATM の入金窓口。伝票（Action）を窓口（Reducer）に出す → 通帳（Store）に記帳 → ATM 画面（View）に新残高表示。

コード例（TypeScript）

import { createStore } from "redux";

type Action = { type: "INC" } | { type: "DEC" };
type State = { count: number };

const reducer = (state: State = { count: 0 }, action: Action): State => {
  switch (action.type) {
    case "INC": return { count: state.count + 1 };
    case "DEC": return { count: state.count - 1 };
    default:    return state;
  }
};

const store = createStore(reducer);
store.dispatch({ type: "INC" });

3. 分散系アーキテクチャ

3.1 Monolithic Architecture

目的と使いどころ

1 つのアプリ／プロセスにすべての機能を詰め込む 最も素朴な構成。スタートアップ初期や PoC、小規模チーム向け。

「分散させる前に、まず動くものを作る」 という意思決定の出発点。

構造イメージ

メリット / デメリット

メリット

  • 開発もデプロイもシンプル（1 箇所更新で完結）

  • 内部関数呼び出しなので高速

デメリット

  • 1 機能の障害が全体停止になる

  • 一部だけスケールアップできない

日常のたとえ

タワーマンション。住居・コンビニ・ジム・駐車場が全部 1 つの建物にある。便利だがエレベーターが止まると全員困る。

コード例（TypeScript）

import express from "express";

const app = express();
app.get("/users",  usersHandler);
app.get("/orders", ordersHandler);
app.get("/billing", billingHandler);
app.post("/notifications", notificationsHandler);
app.listen(3000);

3.2 Modular Monolith

目的と使いどころ

単一プロセスのまま、内部を明確なモジュール境界に分割 する構成。マイクロサービス化の前段としても優れる。

「マイクロサービスの運用コストはまだ払えないが、ドメイン境界は明確にしたい」 中規模プロダクトに最適。

構造イメージ

メリット / デメリット

メリット

  • 単一プロセスの簡便さを保ちつつ、モジュール分離が効く

  • 将来のマイクロサービス化が容易

デメリット

  • 境界を破ってモジュール直参照する誘惑が常にある

  • 規律を組織で守る必要がある

日常のたとえ

シェアハウス。1 棟だが個室は鍵付きで独立、共用は台所だけ。プライバシーを保ちつつ家賃を抑えられる。

コード例（TypeScript）

// modules/user/index.ts
export const UserModule = {
  findById: (id: string) => userRepo.find(id),
};

// modules/order/index.ts
import { UserModule } from "../user";
export const OrderModule = {
  async placeOrder(userId: string, items: Item[]) {
    const user = await UserModule.findById(userId);
  },
};

3.3 Microservices

目的と使いどころ

機能ごとに 独立したサービス としてデプロイし、HTTP / gRPC で連携する構成。サービスごとに DB・技術スタック・担当チームを独立にできる。

大規模組織、複数チーム並走、高可用性が必要なプロダクト向け。

構造イメージ

メリット / デメリット

メリット

  • 独立スケール（売れ筋サービスだけ大きくできる）

  • 障害局所化／独立デプロイ

  • 技術選択の自由

デメリット

  • ネットワーク通信が複雑（タイムアウト・リトライ・整合性）

  • 運用負荷が増大（オブザーバビリティ必須）

日常のたとえ

アメ横の商店街。八百屋・肉屋・魚屋が独立。1 店が閉まっても他は営業継続。各店主は得意分野に集中できる。

コード例（TypeScript）

// user-service/index.ts
app.get("/users/:id", async (req, res) => {
  res.json(await db.users.find(req.params.id));
});

// order-service/index.ts (別プロセス・別DB)
const userRes = await fetch(`http://user-service/users/${userId}`);
const user = await userRes.json();

3.4 SOA (Service-Oriented Architecture)

目的と使いどころ

企業全体をサービス単位で構成し、ESB（Enterprise Service Bus） を中心とした統合を行う。マイクロサービスの源流。

異なるベンダー製の業務システム（CRM・ERP・人事）を統合したい大企業 IT で採用。

構造イメージ

メリット / デメリット

メリット

  • 異なる技術の業務システムを統合できる

  • 共通 ESB により標準化が進む

デメリット

  • ESB がボトルネック／単一障害点になりやすい

  • マイクロサービスより重厚

日常のたとえ

巨大ショッピングモール。各テナントは独立だが、館内放送・ポイントカード・警備が共通。

コード例（TypeScript）

import { ServiceBus } from "enterprise-bus";
const bus = new ServiceBus();

await bus.publish("order.created", { orderId: "123", userId: "u1" });

bus.subscribe("order.created", async (event) => {
  await inventoryService.reserve(event.orderId);
});

3.5 Event-Driven Architecture

目的と使いどころ

イベントの発行 / 購読 で疎結合に通信。発信側は受信側を知らなくていい。

リアルタイム通知、IoT、複数システム連携、CQRS / Event Sourcing の基盤として採用。

構造イメージ

メリット / デメリット

メリット

  • 疎結合で受信側を後から追加可能

  • 非同期スケールしやすい

デメリット

  • イベントの順序保証・重複処理が難しい

  • 全体フローを追うのが大変

日常のたとえ

駅構内放送。「3 番線まもなく発車」と放送される。乗りたい人は走り、関係ない人は無視。アナウンスする側は誰が反応するか知らなくていい。

コード例（TypeScript）

import { Kafka } from "kafkajs";

const kafka = new Kafka({ brokers: ["localhost:9092"] });

const producer = kafka.producer();
await producer.send({
  topic: "order.created",
  messages: [{ value: JSON.stringify({ orderId: "123" }) }],
});

const consumer = kafka.consumer({ groupId: "inventory" });
await consumer.subscribe({ topic: "order.created" });
await consumer.run({
  eachMessage: async ({ message }) => { /* 在庫処理 */ },
});

3.6 Serverless Architecture

目的と使いどころ

FaaS（Function as a Service）と BaaS を組み合わせ、サーバ管理を完全に外部化。リクエストが来たときだけ起動。

トラフィックが時間帯で変動するシステム、イベント駆動の小タスク、PoC で「サーバを立てたくない」場合に最適。

構造イメージ

メリット / デメリット

メリット

  • 運用ゼロ、使った分だけ課金

  • 自動スケール

デメリット

  • コールドスタートで初回応答が遅い

  • ベンダーロック（Lambda 専用記法など）

日常のたとえ

呼ばれた時だけ来るバイト。普段はシフトゼロ、客が来た瞬間だけ呼ばれ、終わったら帰る。雇用側のサーバ運用ゼロ。

コード例（TypeScript）

import type { NextRequest } from "next/server";

export async function POST(req: NextRequest) {
  const body = await req.json();
  return Response.json({ ok: true, received: body });
}

3.7 BFF (Backend for Frontend)

目的と使いどころ

クライアント（Web / iOS / Android）ごとに 専用の API レイヤ を設け、UI に最適化したレスポンスを返す。

マルチプラットフォーム展開で、各クライアントの要件が大きく異なるプロダクトに最適。

構造イメージ

メリット / デメリット

メリット

  • クライアント別最適化（オーバーフェッチ回避）

  • フロント担当者が自分の BFF を所有できる

デメリット

  • BFF が増えるとメンテ負荷増

  • ロジックが BFF に染み込みやすい

日常のたとえ

国際会議の同時通訳。日本語・英語・フランス語の代表団それぞれに専用通訳が付く。中央演説者は 1 人だが各言語向けに最適化される。

コード例（TypeScript）

export async function GET(req: Request) {
  const uid = getUserId(req);
  const [user, orders, notifs] = await Promise.all([
    userSvc.get(uid),
    orderSvc.listRecent(uid, 5),
    notifSvc.unreadCount(uid),
  ]);
  return Response.json({ user, recentOrders: orders, unread: notifs });
}

3.8 Space-Based Architecture

目的と使いどころ

DB のボトルネック回避のため、メモリ上のデータグリッド を中心に水平スケール。永続化は非同期に行う。

チケット販売、オンラインゲーム、株式取引など、瞬間的に高 TPS が要求されるシステム向け。

構造イメージ

メリット / デメリット

メリット

  • DB がボトルネックにならない

  • 水平スケールで高スループット

デメリット

  • メモリ整合性の制御が複雑

  • 障害時にデータ消失リスク（永続化遅延）

日常のたとえ

コンサート会場の入場ゲート。手元タブレットに参加者リストをまるごと配っておき、各ゲートが独立で照合できるようにする。

コード例（TypeScript）

import { createCluster } from "redis";

const cache = createCluster({ rootNodes: [] });
await cache.connect();

await cache.set(`ticket:${id}`, JSON.stringify(ticket));
const ticket = JSON.parse((await cache.get(`ticket:${id}`)) ?? "{}");

queueWriteToDb(ticket);

4. データ／DDD 系パターン

4.1 Repository Pattern

目的と使いどころ

ドメイン層からデータアクセスを抽象化し、コレクション風の I/F でドメインオブジェクトを永続化する。

DB の実装を後から差し替える可能性があるシステム、テストでインメモリ実装を使いたい場合に必須。

構造イメージ

メリット / デメリット

メリット

  • ドメインがインフラを知らない（純粋に保てる）

  • テストでモック実装を差し替え可能

デメリット

  • ORM 自体が既に Repository 的なら二重ラップになる

日常のたとえ

図書館の司書。利用者は「○○の本ありますか」と聞くだけ。本がどの棚にあるかは司書だけが知っている。

コード例（TypeScript）

interface UserRepository {
  findById(id: string): Promise<User | null>;
  save(user: User): Promise<void>;
}

class PrismaUserRepository implements UserRepository {
  async findById(id: string) { return prisma.user.findUnique({ where: { id } }); }
  async save(user: User)     { await prisma.user.upsert({ where: { id: user.id }, update: user, create: user }); }
}

class InMemoryUserRepository implements UserRepository {
  private store = new Map<string, User>();
  async findById(id: string) { return this.store.get(id) ?? null; }
  async save(user: User)     { this.store.set(user.id, user); }
}

4.2 CQRS (Command Query Responsibility Segregation)

目的と使いどころ

書き込み（Command）と読み出し（Query）を別モデル／別ストレージに分離 する。

読み込みが書き込みの 10 倍以上、複雑な集計レポートが必要なシステムに最適。

構造イメージ

メリット / デメリット

メリット

  • 読み書きを独立スケール可能

  • 読み取りに特化した非正規化モデルで高速化

デメリット

  • 結果整合性（読み取り側が一瞬古いデータを返す）を許容する必要

  • 実装複雑度が増す

日常のたとえ

Amazon の倉庫。入荷口（書き込み）と発送口（読み出し）が完全分離。互いを邪魔しない。

コード例（TypeScript）

// === Write 側 ===
class OrderCommandHandler {
  async placeOrder(cmd: PlaceOrderCommand) {
    const order = Order.create(cmd);
    await writeDb.orders.insert(order);
    await eventBus.publish({ type: "OrderPlaced", payload: order });
  }
}

// === Read 側 (非正規化) ===
class OrderQueryService {
  async listByUser(userId: string) {
    return readDb.orders_view.find({ userId });
  }
}

4.3 Event Sourcing

目的と使いどころ

状態そのものを保存せず、状態変化を「イベントの列」として保存 する。任意時点の状態は再生（replay）で復元可能。

金融、会計、規制対応、強い監査要件が必要なシステムに最適。

構造イメージ

メリット / デメリット

メリット

  • 完全な監査ログ（誰がいつ何をしたか残る）

  • タイムトラベル（任意時点の状態を復元）

デメリット

  • スキーマ進化が難しい（過去イベント形式も維持）

  • 学習コスト・実装コストが高い

日常のたとえ

銀行の通帳。「現在残高 10 万円」を記録するのではなく、「+5 万入金、-2 万出金、+7 万入金…」と取引履歴を残す。残高はいつでも計算できる。

コード例（TypeScript）

type Event =
  | { type: "AccountOpened"; userId: string }
  | { type: "Deposited";     amount: number }
  | { type: "Withdrawn";     amount: number };

const eventStore: Event[] = [];

const balance = (events: Event[]): number =>
  events.reduce((b, e) => {
    if (e.type === "Deposited") return b + e.amount;
    if (e.type === "Withdrawn") return b - e.amount;
    return b;
  }, 0);

4.4 DDD (Domain-Driven Design)

目的と使いどころ

ドメインモデルを中心にコードを構造化し、Bounded Context（境界づけられたコンテキスト） で大規模システムを分割。

ドメインが複雑で、ビジネス専門家との会話と実装を一致させたい大規模システム向け。

構造イメージ

メリット / デメリット

メリット

  • 業務とコードが一致する

  • 大規模システムを認知負荷低く分割できる

デメリット

  • 学習コストが高い

  • 過剰適用すると小さな業務にも重厚な構造を入れがち

日常のたとえ

多国籍企業の会議。営業・経理・法務はそれぞれ専門用語が違う。同じ「顧客」も部署ごとに意味が違う。翻訳係（ACL） を間に挟んで部署同士を繋ぐ。

コード例（TypeScript）

class Money {
  constructor(public readonly amount: number, public readonly currency: "JPY" | "USD") {}
  add(other: Money) {
    if (this.currency !== other.currency) throw new Error("通貨不一致");
    return new Money(this.amount + other.amount, this.currency);
  }
}

class Order {
  private items: OrderItem[] = [];
  private status: "draft" | "confirmed" = "draft";
  addItem(item: OrderItem) {
    if (this.status !== "draft") throw new Error("確定後は変更不可");
    this.items.push(item);
  }
  confirm() { this.status = "confirmed"; }
}

5. 統合・移行パターン

5.1 Saga Pattern

目的と使いどころ

分散トランザクションを 「ローカル Tx + 補償処理」 の連鎖で実現。Choreography（イベント駆動）と Orchestration（中央調整）の 2 形式。

マイクロサービスで、複数サービスにまたがる整合性が必要な処理（注文・決済・配送など）に最適。

構造イメージ

メリット / デメリット

メリット

  • マイクロサービス間で整合性を担保できる

  • 各サービスは自分の DB だけ意識すればよい

デメリット

  • 補償処理の設計が難しい（冪等性必須）

  • デバッグが大変

日常のたとえ

旅行予約。航空券 → ホテル → レンタカーの順に予約。レンタカーが失敗したら、ホテルキャンセル → 航空券キャンセルと逆走で巻き戻す。

コード例（TypeScript）

async function bookTrip() {
  const flight = await flightSvc.book();
  try {
    const hotel = await hotelSvc.book();
    try {
      await carSvc.book();
    } catch (e) {
      await hotelSvc.cancel(hotel.id);
      await flightSvc.cancel(flight.id);
      throw e;
    }
  } catch (e) {
    await flightSvc.cancel(flight.id);
    throw e;
  }
}

5.2 Strangler Fig Pattern

目的と使いどころ

レガシーシステムを一気に置き換えず、新システムで少しずつ「絞め殺す」ように段階移行 する。

既存システムが大きすぎてビッグバン移行できない、停止できないサービスをリプレースしたい場合に最適。

構造イメージ

メリット / デメリット

メリット

  • ダウンタイムなしで移行可能

  • 部分ごとに検証しながら進められる

デメリット

  • 新旧並走期間の運用負荷が増える

  • ルーティング層が複雑化

日常のたとえ

駅前再開発。古い駅ビルを使いながら、横に新駅ビルを建ててテナントを少しずつ移していく。最後に古い駅ビルを解体。

コード例（TypeScript）

import { proxyTo } from "./proxy";

app.use("/api/v1/users", async (req, res) => {
  if (await featureFlag.isOn("user-service-migrated", req)) {
    return proxyTo(newUserService, req, res);
  }
  return proxyTo(legacyMonolith, req, res);
});

5.3 Sidecar Pattern

目的と使いどころ

アプリ本体と並走する補助プロセスを同一 Pod に配置し、横断的機能（ログ、認証、メトリクス） を提供する。Service Mesh の基礎。

複数サービスで共通の横断処理を、各言語・各実装に依存せず統一したい場合に最適。

構造イメージ

メリット / デメリット

メリット

  • 横断的関心が言語非依存

  • 本体コードに認証・ログ等の Boilerplate を書かなくて済む

デメリット

  • Pod の構成が複雑化

  • パフォーマンスオーバーヘッドが少しある

日常のたとえ

バイクのサイドカー。バイク本体（アプリ）と並走する補助席（Sidecar）。海外出張に通訳が同行するイメージ。

コード例（TypeScript）

app.get("/orders", async (_, res) => res.json(await listOrders()));
// 認証・ログ・メトリクスは Sidecar (例: Envoy) が透過処理
// docker-compose.yml で同一 Pod に Envoy コンテナを並列起動

5.4 Ambassador Pattern

目的と使いどころ

クライアントの外部通信を Ambassador プロキシ経由 にし、リトライ／サーキットブレーカ／監視を集約する。

外部 SaaS（決済、メール、地図 API）への依存が多く、失敗時の挙動を集中管理したい場合に最適。

構造イメージ

メリット / デメリット

メリット

  • 外部依存を 1 箇所で制御

  • リトライ・タイムアウト・CB を統一

デメリット

  • Ambassador 自身が単一障害点になりうる

日常のたとえ

大使館員。自国市民は直接外国政府と交渉せず、大使館員が代行。

コード例（TypeScript）

class StripeAmbassador {
  async charge(amount: number, currency: string) {
    return retry(3, () =>
      circuitBreaker(() => stripe.charges.create({ amount, currency }))
    );
  }
}

const ambassador = new StripeAmbassador();
await ambassador.charge(1000, "JPY");

5.5 Anti-Corruption Layer (ACL)

目的と使いどころ

自ドメインと外部（レガシー／他社）ドメインの間に 翻訳層 を置き、外部の概念汚染を防ぐ。

レガシーシステムや他社 API の語彙が自ドメインに浸透しないよう、明確に境界を切るときに使う。

構造イメージ

メリット / デメリット

メリット

  • レガシーの呪いから自ドメインを守る

  • 外部 API 変更時の影響を ACL で吸収

デメリット

  • 翻訳コードのメンテが追加で必要

日常のたとえ

海外駐在員。現地の慣習をそのまま日本本社に持ち込まず、本社が理解できる言葉に翻訳する。

コード例（TypeScript）

type LegacyUser = { user_id: string; user_name: string; flg: "0" | "1" };
type DomainUser = { id: string; name: string; isActive: boolean };

const translateUser = (l: LegacyUser): DomainUser => ({
  id: l.user_id,
  name: l.user_name,
  isActive: l.flg === "1",
});

5.6 API Gateway

目的と使いどころ

マイクロサービスの 単一エントリポイント として、認証・レート制限・ルーティング・レスポンス集約を担う。

複数のクライアントが複数のサービスにアクセスするマイクロサービス構成で、横断ポリシーを一元化したい場合に最適。

構造イメージ

メリット / デメリット

メリット

  • 認証・レート制限を集中管理

  • クライアントは Gateway だけ知ればよい

デメリット

  • Gateway がボトルネック／単一障害点になりうる

  • Gateway 自体の運用が必要

日常のたとえ

オフィスビルの受付。来訪者は受付で身分確認 → 行き先の部署へ案内。各部署が個別に来訪者対応せずに済む。

コード例（TypeScript）

import express from "express";
import rateLimit from "express-rate-limit";

const gateway = express();
gateway.use(rateLimit({ max: 100, windowMs: 60_000 }));
gateway.use(authMiddleware);
gateway.use("/users",  proxy("http://user-service"));
gateway.use("/orders", proxy("http://order-service"));
gateway.listen(8080);

6. その他構造系パターン

6.1 Pipe and Filter

目的と使いどころ

データを連続するフィルタに流し込み、各フィルタが入力を変換して次に渡す Unix パイプ思想のパターン。

ETL、コンパイラ、画像処理、ストリーミング処理、データ変換パイプラインに最適。

構造イメージ

メリット / デメリット

メリット

  • 各フィルタが独立してテスト可能

  • 並列化／再利用がしやすい

デメリット

  • 共有状態を持たせにくい

  • フィルタ間のスキーマ整合性が課題

日常のたとえ

回転寿司の調理ライン。シャリ握り → ネタ載せ → わさび付け → レーン送り。各工程は前の工程しか知らない。

コード例（TypeScript）

const pipe = <T>(...fns: Array<(x: T) => T>) =>
  (input: T) => fns.reduce((acc, fn) => fn(acc), input);

const pipeline = pipe(
  parseCsv,
  validate,
  transform,
  enrich,
);

const result = pipeline(rawCsv);

6.2 Vertical Slice Architecture

目的と使いどころ

技術レイヤで分割せず、「機能（Feature）」で縦に切る。各機能内に Controller / Logic / Data がまとまる。

機能追加が多く、レイヤ間の変更コストを減らしたいプロジェクトに最適。CQRS + MediatR との相性◎。

構造イメージ

メリット / デメリット

メリット

  • 機能追加が 1 箇所で完結

  • 変更影響範囲が局所化

デメリット

  • スライス間のコード重複が起きやすい

  • 共通ロジックの抽出タイミング判断が難しい

日常のたとえ

ケーキの縦切り。チョコケーキを縦に切ると、各皿に「スポンジ・クリーム・チョコ」が全部揃う。

コード例（TypeScript）

// features/create-order/handler.ts
import { parseCreateOrder } from "./validation";
import { createOrderInDb } from "./repository";
import { notifyCustomer } from "./notify";

export const createOrderHandler = async (req: Request) => {
  const body  = parseCreateOrder(await req.json());
  const order = await createOrderInDb(body);
  await notifyCustomer(order);
  return Response.json({ id: order.id });
};

6.3 Component-Based Architecture

目的と使いどころ

UI または機能を 独立した再利用可能なコンポーネント で構成。React / Vue / Web Components の基盤思想。

モダンな Web フロントエンド開発で標準的に採用される。

構造イメージ

メリット / デメリット

メリット

  • 再利用性が高い

  • 単体テストが容易

デメリット

  • 過剰分割で組み立てが複雑化

  • 状態を多くのコンポーネントに分散させると追跡困難

日常のたとえ

レゴブロック。屋根ブロック・窓ブロック・ドアブロックを組み合わせて家を作る。1 つの部品は他の家でも再利用できる。

コード例（TypeScript）

function Button({ onClick, label }: { onClick: () => void; label: string }) {
  return <button onClick={onClick}>{label}</button>;
}

function Card({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      {children}
    </section>
  );
}

function Page() {
  return <Card title="設定"><Button onClick={save} label="保存" /></Card>;
}

6.4 Client-Server

目的と使いどころ

最も基本的な分散構造。クライアントがサーバにリクエストし、サーバが応答する。

Web、モバイルアプリ、デスクトップアプリの大多数で採用される標準形。

構造イメージ

メリット / デメリット

メリット

  • 学習コストが低く、業界標準

  • サーバー側でセキュリティ・整合性を集中管理

デメリット

  • サーバー障害で全クライアントが影響

  • スケールにロードバランサ等の追加コスト

日常のたとえ

牛丼チェーン。客（Client）が「並、つゆだく」と注文、店員（Server）が作って渡す。

コード例（TypeScript）

// Server
import express from "express";
const app = express();
app.get("/api/hello", (_, res) => res.json({ msg: "hello" }));
app.listen(3000);

// Client
const result = await fetch("/api/hello").then((r) => r.json());
console.log(result.msg);

6.5 Peer-to-Peer

目的と使いどころ

各ノードが対等に クライアントとサーバの両役 を担う構造。中央集約のサーバを持たない。

BitTorrent、ブロックチェーン、IPFS、WebRTC ベースのビデオ通話などで採用。

構造イメージ

メリット / デメリット

メリット

  • 中央サーバ不要、検閲耐性が高い

  • スケールしやすい（参加者が増えるほど資源も増える）

デメリット

  • ピア発見・NAT 越え・セキュリティが複雑

  • ガバナンスが効きにくい

日常のたとえ

メルカリ。全ユーザーが出品者にも購入者にもなる。中央の店長はいない（運営は仲介のみ）。

コード例（TypeScript）

const pc = new RTCPeerConnection();
const dc = pc.createDataChannel("chat");

dc.onopen    = () => console.log("接続");
dc.onmessage = (e) => console.log("相手:", e.data);

dc.send("やあ、ピアくん");

6.6 Broker / Blackboard

目的と使いどころ

Broker: 分散コンポーネント間の通信を仲介。 Blackboard: 共有データ空間に各専門コンポーネント（Knowledge Source）が読み書きし、協調して解を構築。

AI システム、音声認識、専門家システム、複雑な推論を多段で組み立てるドメインで採用。

構造イメージ

メリット / デメリット

メリット

  • 専門領域ごとにモジュール独立

  • 部分的知識でも協調して解に近づける

デメリット

  • 共有状態の整合性管理が複雑

  • 古典的でモダンな代替（Event-Driven 等）が存在

日常のたとえ

会議室のホワイトボード。営業・開発・経理が各自の専門分野で書き込み、他の人の書き込みも参照して企画書を完成させる。

コード例（TypeScript）

const blackboard: Record<string, unknown> = {};

const phonemeKS = (audio: Buffer) => {
  blackboard.phonemes = analyze(audio);
};
const wordKS = () => {
  if (blackboard.phonemes) blackboard.words = group(blackboard.phonemes);
};
const sentenceKS = () => {
  if (blackboard.words) blackboard.sentence = assemble(blackboard.words);
};

6.7 JAMstack

目的と使いどころ

JavaScript + APIs + Markup。静的サイト生成 + CDN 配信 + 動的部分は API で実現。

ブログ、マーケサイト、ドキュメント、E コマースのフロントエンドに最適。

構造イメージ

メリット / デメリット

メリット

  • 圧倒的に速い（CDN 配信）

  • セキュリティ／インフラ運用が軽い

デメリット

  • ビルド時間が長くなりがち

  • 完全動的なページには向かない

日常のたとえ

コンビニ。完成品の弁当（静的サイト）が棚に並んで取るだけ。注文・決済（API）はレジで別途。陳列と業務処理が完全分離。

コード例（TypeScript）

export const revalidate = 3600;

export default async function PostsPage() {
  const posts = await fetch("https://cms.example.com/posts", {
    next: { revalidate: 3600 },
  }).then((r) => r.json());

  return (
    <ul>{posts.map((p: Post) => <li key={p.id}>{p.title}</li>)}</ul>
  );
}

まとめ

設計パターンに 唯一の正解はない。プロダクト規模、チーム人数、ドメインの複雑さ、変更速度の要求によって最適解は変わる。

押さえるべき原則は 3 つ:

  1. 「変わらないもの」を中心に置く — ビジネスルールは外部の道具より変わりにくい

  2. 「責任を分離する」 — 1 つの場所に複数の責任を持たせると変更が連鎖する

  3. 「早すぎる最適化は害」 — 最初から完璧を狙わず、必要になったら段階的に進化させる

設計は、コードを書く前の 「家の図面」 に相当する。図面が良ければ建築は速い。逆に図面が雑だと、住んでから後悔する。
