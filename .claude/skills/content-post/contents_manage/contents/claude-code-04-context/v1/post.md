> **この章のゴール**
> - コンテキスト（Claudeが今ぱっと思い出せる情報の総量）の **積み上げ順** を理解する
> - `CLAUDE.md`（プロジェクトの指示書）を効果的に書ける
> - `/context` `/compact` `/branch` を使い分けられる
> - 不要なコンテキストで精度が落ちる仕組みを理解する

**所要時間：約60分**

---

## 1. なぜ「コンテキスト」が一番大事なのか

LLM には **注意の上限** があります。一度に意識できるのはざっくり 150〜200個ぐらいの情報まで、と言われていて、**それ以上を詰め込むと精度がガクッと落ちる** んです。

人間でも同じですよね。**机の上が書類で埋め尽くされてると、肝心な書類を見落とす。** あれと同じです。

Claude Code はコンテキストウィンドウ（一度に取り込める文字数の枠）が 200K（約20万トークン）まで入りますが、

> **80%超えてからは急速に賢くなくなる。65〜70%でコンパクション（履歴の圧縮）が理想。**
> — 数理の弾丸動画より

つまり「20万トークン入る」≠「20万トークン使い切ってOK」。**いかに余裕を持って動かすか** が腕の見せどころなんです。

---

## 2. コンテキストの積み上げ順

セッション中に **`/context`** コマンドを実行すると、いま何が机の上に積まれているか可視化できます。**「いまの机の上、何が乗ってる？」を見る道具** ですね。

![](./images/inline/ch04-m1.png)

積み上がりの **重要なポイント**：

1. **①〜⑤ は起動時に固定で積まれる** → 余計なものを入れると毎回トークンを浪費（**毎日カバンに使わない教科書を入れて学校に行ってる感じ**）
2. **⑥ CLAUDE.md** はあなたが書いた指示書 → ここを **太らせるな**（あとで詳述）
3. **⑦ メッセージ履歴** が伸びるほどコンテキスト圧迫 → `/clear` `/compact` `/branch` で管理
4. **MCPサーバー（外部サービス連携）の説明** はサーバー数だけ膨らむ → 不要なものは外す

 **やってみる**：起動直後に `/context` で何が積まれているか見てみてください。**意外と最初から色々乗ってるな、と気づきます**。

## 3. CLAUDE.md：プロジェクトの指示書

### 3-1. 役割

`CLAUDE.md` はプロジェクトのルート（一番上の階層）に置く Markdown ファイル。**毎セッション自動で読み込まれて** 文脈に注入されます。**「家に来た人がまず最初に読む張り紙」** だと思ってください。

### 3-2. 階層と読み込み順

![](./images/inline/ch04-m2.png)

### 3-3. 注意点

| 注意 | 内容 |
|---|---|
| 兄弟ディレクトリ（隣の同じ階層のフォルダ）は読まれない | 横並びの別フォルダの CLAUDE.md は無視される |
| 子ディレクトリも自動では読まない | ファイルにアクセスした時に **遅延ロード**（必要になってから読む） される |
| `settings.json`（環境設定ファイル）は逆 | こちらは「プロジェクト側が優先」で上書きされる |

### 3-4. 何を書くべきか

書いていいもの：

-  プロジェクトの目的・ゴール
-  ディレクトリ構造（簡潔に）
-  使用する言語・フレームワーク・固有名詞（**具体的に**）
-  禁止事項（「main に直接コミット禁止」など）
-  コーディング規約のキモだけ
-  詳細はどこを見るかの **ポインター**（参照先の案内、後述）

書いてはいけないもの：

-  ありとあらゆる詳細（注意力を奪う）
-  一回限りの事情（PR説明文に書くべき）
-  Linter（コードの自動チェックツール）で機械的にチェックできる規約（自動化に任せるべき）
-  暗黙知のすべて（書ききれない）

>  **CLAUDE.md は「ダイエットしたい」**：書きたくなる気持ちは分かるんですが、太れば太るほど Claude の注意力が削られます。**「最低限、これだけは知っておいて」だけ書くのがコツ**。

### 3-5. 段階的開示（Progressive Disclosure）

CLAUDE.md は **概要 + ポインター** にとどめて、詳細はサブドキュメント（補助資料）へ。**「お品書きには概要だけ書いて、詳しい食材リストは別冊」** のイメージです。

![](./images/inline/ch04-m3.png)

CLAUDE.md には：

> このプロジェクトのアーキテクチャは `docs/architecture.md` を参照してください。

と書いておくだけ。これで CLAUDE.md は痩せたまま、必要な時だけ詳細が読まれる、という仕組み。これが [第5回](/articles/claude-code-05-skills-and-commands) で扱う **スキル**（必要なときだけ読む専門知識）の本質と同じ考え方です。

### 3-6. テンプレート

そのまま使えるテンプレートを置いておきます。**最初はこれをコピペして、自分のプロジェクトに合わせて削るのが早い** です。

```markdown
# CLAUDE.md

## このプロジェクトについて
（1〜3行で目的を書く）

## 開発方針
- TDD（Test-Driven Development = テストを先に書く開発スタイル。Red → Green → Refactor）
- 言語: TypeScript / Node.js 22 LTS
- フレームワーク: Next.js App Router
- スタイル: shadcn/ui + Tailwind v4

## ディレクトリ
- src/ — アプリ本体
- tests/ — テスト
- docs/ — 設計資料・規約集

## 禁止事項
- ⚠️ main ブランチへの直接コミット
- ⚠️ 仕様変更を伴うリファクタリング（コード書き直し）はタスク化してから

## 詳細は以下を参照
- アーキテクチャ: docs/architecture.md
- コーディング規約: docs/conventions.md
- 認証フロー: docs/auth-flow.md
```

## 4. Rules（スコープ付きルール）

### 4-1. Rules とは

Rules（ルール）は、`.claude/rules/` ディレクトリに置く Markdown ファイル。**特定のパス・特定の条件で自動ロードされる** Claude 用の指示書なんですよ。

CLAUDE.md と何が違うかというと、こんな感じです。

| 観点 | CLAUDE.md | Rules |
|---|---|---|
| 読み込みタイミング | セッション開始時に常時 | パス・条件にマッチしたとき |
| スコープ（適用範囲） | プロジェクト全体 | 特定のパス配下のみ |
| 用途 | プロジェクト概要・全体方針 | 特定領域の詳細ルール |

例えるなら、**CLAUDE.md = 会社の就業規則（全社共通）、Rules = 各部署のローカルルール（部門固有）**。両方とも効きますが、Rules は **該当する部門に行ったときにだけ** 読まれます。

### 4-2. ディレクトリ構成

```text
.claude/rules/
├── communication.md     ← 常時ロード（コミュニケーション作法）
├── development.md       ← src/**, tests/** 配下で自動ロード
└── task-flow.md         ← docs/tasks/**, docs/draft/** で自動ロード
```

### 4-3. ファイルの書き方（フロントマター）

```markdown
---
description: コーディング規約・TDD ガイド
glob: src/**, tests/**
---

# Development Rules

ここに本文（規約・手順・禁止事項など）
```

| フィールド | 説明 |
|---|---|
| `description` | このルールの目的（一行で） |
| `glob` | 自動ロードするパスパターン（**指定なし=常時ロード**） |

### 4-4. なぜ Rules を使うか：コンテキストを膨張させない

ぶっちゃけ、CLAUDE.md に「コーディング規約」「議事録テンプレ」「認証フロー詳細」と全部詰め込むと、Claude が **毎セッションで全部読まされて** コンテキスト（机のスペース）が一気に圧迫されます。

![](./images/inline/ch04-m4.png)

Rules を使うと、こうなります。

- **コーディングしているとき** だけ `development.md` を読む
- **議事録作成時** だけ `meeting-notes.md` を読む
- **タスク管理画面** に行ったときだけ `task-flow.md` を読む

普段は **「あるけど寝てる」** 状態。Claude が必要な場面に来てはじめて「お、これ読まなきゃ」と起こされる、というイメージです。

### 4-5. CLAUDE.md と Rules の使い分けベストプラクティス

CLAUDE.md は **目次（索引）** に徹して、詳細は Rules に分散させる。これが鉄則。

```markdown
# CLAUDE.md (索引のみ・薄く保つ)

## このプロジェクトについて
（1〜3行で目的を書く）

## 詳細ルール（必要時に Claude が読みに行く）
- コーディング: .claude/rules/development.md（src/, tests/ で自動ロード）
- コミュニケーション: .claude/rules/communication.md（常時ロード）
- タスクフロー: .claude/rules/task-flow.md（docs/ で自動ロード）
- 認証フロー: docs/auth-flow.md（必要時 @ で参照）
```

これで CLAUDE.md は **薄く、Claude は必要時にだけ詳細を読む** 状態になります。**会社のマニュアルを一冊にまとめず、章ごとに別冊にする発想** ですね。

### 4-6. アンチパターン

「これやりがちだけどダメ」をまとめておきます。

| ダメパターン | なぜダメ | 直し方 |
|---|---|---|
| すべて CLAUDE.md に詰める | コンテキスト膨張・注意力低下 | rules / docs に分離 |
| Rules の `glob` が広すぎ | 不要時にも読まれる | 適切なパス絞り込み |
| Rules 同士で内容が重複 | 矛盾の温床 | 1つにまとめる or 役割分離 |
| Rules を作らず `@` で毎回手動指定 | 自動化の利点を失う | autoload を活用 |

### 4-7. 第12回のサンプルハーネスで体験する

実際の Rules 設計は [第12回のサンプルハーネス](/articles/claude-code-12-sample-harness) に同梱されています。`development.md` `communication.md` `task-flow.md` の3ファイルが配置済みなので、**動かしてみるのが一番早い** です。

## 5. 自動メモリ（Auto Memory）

Claude Code は会話の中で「これは覚えておくべき」と判断したことを `~/.claude/projects/<path>/memory.md`（プロジェクト用のメモ置き場）に **自動保存** します。**机に勝手に付箋を貼っていく** イメージ。

| 操作 | 動作 |
|---|---|
| `/memory` | メモリの一覧と中身を表示 |
| 自動 | 「このコマンドはビルド用」のような気付きが蓄積 |

>  **動画より**：自動メモリは便利な反面、**ノイズ（不要な情報）が溜まりやすい** という声も多いです。**気がつくと付箋だらけの机になってる** やつ。気になるなら `/memory` で定期的にチェック・整理。

## 6. メッセージ履歴の管理：3つのテクニック

会話が長くなってきたら、3つの選択肢があります。

![](./images/inline/ch04-m5.png)

### 5-1. `/clear` — リセット

履歴を全部消して、CLAUDE.md と組み込みツールだけの状態に戻ります。**話題を完全に切り替えるとき**。**ホワイトボードを消して書き直す感覚** です。

### 5-2. `/compact` — 圧縮

会話履歴を **要約** して短くする機能。Claude が「ここまでに何をしてきたか」のサマリーを作って、それで履歴を置き換える。**書類を要約してファイリングする感じ** です。

| 設定 | 内容 |
|---|---|
| デフォルト発火（自動で動くタイミング） | コンテキストの **約83.5%** を超えたとき自動 |
| 閾値（しきいち = ボーダーライン）変更 | 環境変数 `CLAUDE_AUTO_COMPACT_PERCENTAGE_OVERRIDE` |
| 推奨 | **60〜70%** に下げる（精度を保つため） |
| 手動実行 | `/compact` |

>  デフォルトの83.5%は「ギリギリまで粘る」設定。**精度重視なら早めに発火させた方がいい**、というのが現場の声です。

### 5-3. `/branch` — 分岐

「いまの会話を引き継いだまま、別の方向も試したい」とき。**ゲームの「セーブして別ルートも試す」** ノリです。

![](./images/inline/ch04-m6.png)

セッション履歴は `~/.claude/projects/<dir>/*.jsonl`（履歴ファイルが置かれる場所）に保存されます。**分岐したい先のディレクトリに JSONL ファイルをコピーすれば、別作業ディレクトリでも履歴を引き継げる** という小技も（[第13回Tip](/articles/claude-code-13-tips-techniques)）。

---

## 7. セッション履歴の保持期間

| 設定 | デフォルト | 変更 |
|---|---|---|
| `cleanupPeriodDays`（履歴を残す日数） | 30日 | `~/.claude/settings.json` で変更可 |

```json
{
  "cleanupPeriodDays": 365
}
```

ハードディスクは少し圧迫しますが、**昔のセッションを呼び出して再開** したい人には設定をおすすめ。**「あのときどう解決したっけ？」を半年後でも引っ張れる** のは結構強いです。

## 8. コンテキスト節約のチェックリスト

セッションが重い・精度が落ちてきた、と感じたら：

| | チェック |
|---|---|
|  | `/context` で何が積まれているか見る |
|  | 不要な MCP サーバー（外部連携）を外す |
|  | CLAUDE.md が太りすぎていないか |
|  | スキル（専門知識ファイル）が大量にロードされていないか |
|  | `/compact` で圧縮 |
|  | 別話題なら `/clear` |
|  | サブエージェント（[第6回](/articles/claude-code-06-subagents)）に切り出す |
