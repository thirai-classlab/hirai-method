# Salesforce オブジェクト設定入門 — Jr.エンジニア向け

**対象**: Salesforce のオブジェクト・項目設定に初めて触れる Jr.エンジニア
**ゴール**: 「標準/カスタムオブジェクト / 項目型 / リレーション / レイアウト / レコードタイプ / 入力規則 / 数式 / 自動化」を説明でき、要件から正しい設定を選べる状態になる

---

## 0. はじめに — なぜ Salesforce のオブジェクト設定は「層」になっているのか

Salesforce のオブジェクト設定は **「データ構造の定義 → 入力UI → 業務ルール → 自動化」の4段** に分かれています。RDB に例えると、項目定義が `CREATE TABLE`、ページレイアウトが入力フォーム、入力規則が `CHECK CONSTRAINT`、フローが `TRIGGER`/`STORED PROCEDURE` を担当するイメージ。

- 営業は商談入力時に「顧客」「金額」「フェーズ」を必須にしたい
- 経理は契約後にしか出ない項目だけ追加で見たい
- マネージャは閉じた案件には編集を禁止したい
- システムは特定条件で自動的に ToDo を作成したい

これを破綻なく扱うために **層構造** にしてあり、まずはこの層を掴むのが最短の理解ルートです。

## 1. 全体像 — オブジェクト設定の 4 段モデル

Salesforce のオブジェクト設定は **4段** で考えます。

<img src="https://d2f75plg0t6qwk.cloudfront.net/tech_article/sf-object-config-tech-jr/3330f885-01.png" alt="1. 全体像 — オブジェクト設定の 4 段モデル （フロー図 縦）" width="1536" height="1024">

| 層 | 質問 | 主な設定項目 |
|----|------|-------------|
| スキーマ層 | 「**何を**保存するか」 | オブジェクト / 項目 / リレーション |
| UI層 | 「**どう入力・表示**するか」 | ページレイアウト / コンパクトレイアウト / レコードタイプ / リストビュー |
| ルール層 | 「**何を許す/拒む**か」 | 入力規則 / 必須項目 / 重複ルール |
| 自動化層 | 「**何を自動でやる**か」 | フロー / 承認プロセス / Apex |

> 💡 **Jr.向けポイント**: 「保存できない」「項目が出ない」時は、まずどの層の問題かを切り分ける癖をつける。**スキーマ → レイアウト → ルール → 自動化** の順で疑う。

## 🎯 各機能の要点早見表 (Jr.エンジニア向け: 機能 / 役割 / 他との違い / ユースケース)

### A. 9機能を1枚で俯瞰

| 機能 | 機能 (何をするもの) | 役割 (どの層) | 他との違い | 代表ユースケース |
|------|------------------|-----------|----------|---------------|
| **オブジェクト** | データを格納する「テーブル」 | スキーマ層 | 標準は既製、カスタムは自由作成 | 「契約案件」「物件情報」をカスタムで作成 |
| **項目** | レコードの「列・型」 | スキーマ層 | 型ごとに動作・表示が違う、後から型変更は制約あり | 金額（通貨）、フェーズ（選択リスト） |
| **リレーション** | オブジェクト間の参照 (FK) | スキーマ層 | 参照関係 vs 主従関係 で削除挙動・共有・積み上げ集計可否が違う | 商談 → 取引先（参照関係）、商品明細 → 商談（主従関係） |
| **ページレイアウト** | レコード詳細画面の入力フォーム | UI層 | プロファイル × レコードタイプで切替可 | 営業用と経理用でレイアウト分岐 |
| **レコードタイプ** | プロセス別の入力経路 | UI層 | レイアウトと選択リストの値を切り替える | 「新規契約」「更新契約」で項目を分岐 |
| **リストビュー** | 一覧画面の絞込・並び・列 | UI層 | ユーザ単位の絞込ビュー | 「自分の今月の案件」「未着手のケース」 |
| **入力規則** | 入力時のチェック | ルール層 | DB CHECK 制約相当、保存阻止 | 「金額>0」「契約日が未来」必須 |
| **数式項目** | 計算結果を表示する読み取り専用列 | スキーマ層 | 保存しない、参照時に計算 | 税込金額、契約期間日数 |
| **積み上げ集計項目** | 子レコードの集計値 | スキーマ層 | **主従関係 必須**、データとして保存 | 商談明細の合計が商談ヘッダに |

**💡 1行サマリ**
> 「**何を保存するか**」は **オブジェクト + 項目 + リレーション**
> 「**どう入力・表示するか**」は **ページレイアウト + レコードタイプ + リストビュー**
> 「**何を許すか**」は **入力規則 + 必須項目 + 重複ルール**
> 「**何を自動でやるか**」は **フロー + 承認プロセス + Apex**

### B. 「参照関係 vs 主従関係」 — 一番混同しやすい関係定義

| 観点 | 参照関係 | 主従関係 |
|------|------|--------------|
| 親なし | 許容（孤立OK） | **不可**（必ず親が必要） |
| 親削除時 | 子は残る（またはエラー） | **子も削除**（カスケード） |
| 共有設定 | 子が独自に持つ | **親に従属**（親で制御） |
| 積み上げ集計項目 | ❌ 作れない | ✅ 作れる |
| 親変更 | 自由 | 設定で許可した時のみ可 |
| 1レコードあたり | 最大25個 | 最大2個まで |
| 代表ユースケース | 商談 → 担当者（担当者削除しても商談を残す） | 商品明細 → 商談（商談が消えたら明細も消す） |

**Jr.の判断基準:**
- **「親が消えたら子も消える」** が業務的に正しいなら主従関係
- **「親が消えても子を残したい」** なら参照関係
- **「子を集計したい（合計/件数）」** なら主従関係必須
- 迷ったら **参照関係から始める**。後から主従関係に変換可（条件付き）

### C. 「項目型 13選」 — 試験に出る型の使い分け

| 型 | 用途 | 注意点 |
|----|-----|-------|
| **テキスト** | 短文（255字まで） | インデックス可、一意制約可 |
| **テキストエリア** | 長文（32,768字まで） | リッチテキストは別型 |
| **数値** | 整数・小数 | 桁数（長さ）と小数点（小数桁数）を別指定 |
| **通貨** | 金額 | 通貨単位、複数通貨対応 |
| **パーセント** | パーセント | 0.5 = 50% ではなく 50 = 50% で保存 |
| **日付** | 日付のみ | タイムゾーン非依存 |
| **日付/時間** | 日付 + 時刻 | タイムゾーン考慮 |
| **メール** | メール | 形式チェック内蔵 |
| **電話** | 電話番号 | 自動フォーマット（米国形式） |
| **URL** | URL | 形式チェック + リンク化 |
| **選択リスト** | 選択肢 | 単一/複数、レコードタイプ別制御可 |
| **チェックボックス** | 真偽値 | デフォルト値設定可 |
| **参照関係 / 主従関係** | 関連 | §B 参照 |
| **数式** | 計算結果 | 読み取り専用、保存しない |
| **積み上げ集計項目** | 子の集計 | **主従関係必須** |
| **自動採番** | 自動採番 | 例: `OPP-{0000}` |
| **位置情報** | 緯度経度 | DISTANCE 関数で距離計算 |

> ⚠️ **型変換の落とし穴**: テキスト → 選択リスト は OK、選択リスト → テキスト は OK、しかし **数値 → テキスト は不可逆**。型変更前に必ずバックアップ。

### D. 「ページレイアウト vs レコードタイプ vs Lightning レコードページ」 — UI 3層

| 観点 | ページレイアウト | レコードタイプ | Lightning レコードページ |
|------|-----------|-----------|---------------------|
| 役割 | 項目の配置 + 関連リスト | プロセス分岐（選択リスト値 + ページレイアウト） | コンポーネント配置（タブ / パス / サイドバー） |
| 必須 | 1つは必要 | 任意（使わなくても可） | 任意（Lightning 環境のみ） |
| 切替軸 | プロファイル × レコードタイプ | プロファイルごとに割当 | アプリ / レコードタイプ / プロファイル |
| 編集 | レイアウトエディタ（古UI） | 設定 > オブジェクト > レコードタイプ | Lightning アプリケーションビルダー |
| 代表ユースケース | 「経理用に金額セクションを上に」 | 「新規契約」と「更新契約」で項目分岐 | 「営業用にパス表示」「マネージャ用に集計タブ」 |

**Jr.の判断基準:**
- 1つのプロセスで項目並びだけ変えたい → ページレイアウトのみ
- プロセスごとに選択リスト値を変えたい → レコードタイプを作る（ページレイアウトも別途必要）
- Lightning 画面でコンポーネント差し替えたい → Lightning レコードページ

### E. 「入力規則 vs 必須項目 vs フロー」 — 入力制御の3手段

| 観点 | 入力規則 | 必須項目（ページレイアウト） | フロー（保存前） |
|------|---------------|-----------------|------------------|
| 効くタイミング | 保存時 | 画面入力時 | 保存直前（ページレイアウトを経由しない API も適用） |
| 経路 | UI / API 両方 | UI のみ | UI / API 両方 |
| 複雑な条件 | 可（数式） | 不可（固定） | 可（決定要素） |
| エラー表示位置 | 指定可 | 項目横に固定 | カスタム可 |
| 自動補正 | 不可（拒否のみ） | 不可 | 可（値を書き換え可能） |
| 代表ユースケース | 「金額>0」「日付未来」 | 「商談名」「フェーズ」必須 | 「フェーズが 受注 なら確度を100に強制」 |

**Jr.の鉄則:**
- **静的な必須化** → 必須項目（ページレイアウト）
- **条件付き必須・複雑チェック** → 入力規則
- **値の自動補正・派生計算** → 保存前フロー
- API インポート時もチェックしたい → 入力規則かフロー

### F. 「数式項目 vs 積み上げ集計項目 vs フローによる更新」 — 派生値の3手段

| 観点 | 数式項目 | 積み上げ集計項目 | フロー（保存後）で更新 |
|------|-------------|---------------|----------------------|
| データ保存 | しない（参照時計算） | する（再計算は SF が管理） | する |
| 集計対象 | 自レコード or 親参照 | **子レコード集計** | 任意 |
| 必要な関係 | なし or 参照関係 | **主従関係必須** | なし |
| パフォーマンス | 高（計算は表示時のみ） | 中（再計算負荷あり） | 低（DML 実行） |
| レポート使用 | 可 | 可 | 可 |
| 代表ユースケース | 税込金額、契約期間日数 | 商談明細の合計、ケース件数 | 親の最新ステータス、複雑な集計 |

**Jr.の鉄則:**
- **計算するだけで保存不要** → 数式項目
- **子の合計/件数を持ちたい（主従関係あり）** → 積み上げ集計項目
- **参照関係で集計したい / 複雑な集計** → フロー + Get Records

### G. 「フローの4種類」 — 自動化の使い分け

| 種類 | 起動契機 | 代表ユースケース |
|------|--------|---------------|
| **画面フロー** | ユーザがボタン押下 | ガイド付き入力ウィザード、複数オブジェクト一括登録 |
| **レコードトリガーフロー** | レコード CRUD | 保存時に値補正、関連レコード生成、メール送信 |
| **スケジュールフロー** | 時刻起動（cron的） | 毎朝の停滞案件抽出、月次バッチ |
| **自動起動フロー** | 他フロー / Apex / プロセスから呼出 | 共通サブルーチン、再利用可能ロジック |

**レコードトリガーフローの起動タイミング:**

<img src="https://d2f75plg0t6qwk.cloudfront.net/tech_article/sf-object-config-tech-jr/16940723-02.png" alt="レコードトリガーフロー 実行順序 (保存 → 保存前フロー → 入力規則 → DBコミット → 保存後フロー → トリガ → ワークフロー → 積み上げ集計 → 完了)" width="1536" height="1024">

> 💡 **保存前フロー vs 保存後フロー**: 保存前は同レコードの値を書き換え、DML が走らないので高速。保存後は他オブジェクト操作・メール送信に使う。

### H. 「列の追加 vs 行の検証 vs リレーションの確立」 — サンプルレコードで可視化

Jr.エンジニアが一番腹落ちしにくいのが **「項目・入力規則・リレーションはそれぞれ何を実現するのか」** です。
答えは **「効く対象が違う」** から。テーブルで見ると明快になります。

#### 📋 サンプル: 物件契約管理オブジェクトの設計 — 生データ要件

「ライフライン契約案件 (Contract__c)」を管理したい。要件:
1. 契約には必ず物件 (Property__c) が紐づく
2. 物件には複数の契約が紐づく（1物件に電気・ガス・水道で別契約）
3. 金額は0より大きく、契約日は未来日付
4. 契約フェーズが 受注 のとき確度は 100% 固定
5. 物件ごとの契約合計金額を物件側で集計表示

#### 🟦 ステップ1 — オブジェクト + 項目（列を作る）

| オブジェクト | 項目名 | 型 | 必須 | 説明 |
|--------|---------|----|----|------|
| Property__c | Name | テキスト | ✅ | 物件名 |
| Property__c | Address__c | テキストエリア | ✅ | 住所 |
| Property__c | Total_Amount__c | 積み上げ集計項目 | - | 契約合計 |
| Contract__c | Name | 自動採番 | - | `CON-{0000}` |
| Contract__c | Property__c | 主従関係 (Property__c) | ✅ | 親物件 |
| Contract__c | Amount__c | 通貨 | ✅ | 契約金額 |
| Contract__c | Contract_Date__c | 日付 | ✅ | 契約日 |
| Contract__c | Stage__c | 選択リスト | ✅ | 検討 / 交渉/レビュー / 受注 / 失注 |
| Contract__c | Probability__c | パーセント | ✅ | 確度 |
| Contract__c | Tax_Included__c | 数式（通貨） | - | `Amount__c * 1.1` |

→ **列の枠組み**ができた。データはまだ無効入力も入る。

#### 🟨 ステップ2 — リレーション（行同士をつなぐ）

<img src="https://d2f75plg0t6qwk.cloudfront.net/tech_article/sf-object-config-tech-jr/cba118e5-03.png" alt="🟨 ステップ2 — リレーション (行同士をつなぐ) （フロー図 縦）" width="1536" height="1024">

→ **主従関係** にしたので:
- 物件削除時に契約も自動削除
- 物件側で `Total_Amount__c = SUM(Contract__c.Amount__c)` の積み上げ集計項目が作れる
- 契約の共有は物件と同じ（親で制御）

#### 🟩 ステップ3 — 入力規則（行の正しさを担保）

```
入力規則 1: 金額は0より大きい
  ルール名: Amount_Must_Be_Positive
  数式: Amount__c <= 0
  エラーメッセージ: "契約金額は0より大きい値を入力してください"
  エラー表示位置: 項目 (Amount__c)

入力規則 2: 契約日は未来
  ルール名: Contract_Date_Future
  数式: Contract_Date__c < TODAY()
  エラーメッセージ: "契約日は今日以降を指定してください"
  エラー表示位置: 項目 (Contract_Date__c)
```

→ **不正な行**が DB に入らなくなる。

#### 🟪 ステップ4 — フロー（条件付き自動補正）

```
レコードトリガーフロー (保存前):
  オブジェクト: Contract__c
  トリガ: 作成または更新
  条件: ISCHANGED(Stage__c) AND Stage__c = "Closed Won"
  アクション: Probability__c = 100
```

→ 受注 に変えた瞬間、確度は100に**自動補正**。入力規則では「拒否」しかできないが、フローでは「書き換え」ができる。

#### 🎯 まとめ: 制御軸 × 効くタイミング

<img src="https://d2f75plg0t6qwk.cloudfront.net/tech_article/sf-object-config-tech-jr/6eb6778c-01.png" alt="実行順序 — レコード保存時の実行順 (必須 → 保存前フロー → 入力規則 → 主従関係 → 保存後フロー / 積み上げ集計)" width="3072" height="1728">

#### 💡 Jr.が覚えるべき1行メッセージ

> **項目 = 「列の定義」(構造)**
> **リレーション = 「行同士の関係」(結合)**
> **入力規則 = 「行の正しさ」(保存可否)**
> **フロー = 「保存前後の自動処理」(派生・連鎖)**
>
> どれか1つが欠けると業務が成立しない。**スキーマ → リレーション → ルール → 自動化** の順で設計する。

## 2. オブジェクト (Object) — 「データのテーブル」

### 2.1 標準オブジェクト

Salesforce が事前定義している既製テーブル。代表例:

| オブジェクト | 用途 |
|--------|-----|
| 取引先 (Account) | 会社情報 |
| 取引先責任者 (Contact) | 取引先に紐づく担当者（人） |

| 商談 (Opportunity) | 案件 |
| ケース (Case) | サポート問合せ |
| 商品 (Product) | 商品マスタ |
| 価格表 (Pricebook) | 価格表 |

### 2.2 カスタムオブジェクト

要件に応じて Admin が作成。API 参照名は **`__c`** が末尾に自動付与。

```
オブジェクトラベル: 物件
API 参照名: Property__c
複数形: 物件
レコード名: 物件名 (Text) または 自動採番
ヘルプテキスト、説明
レポート / 活動 / 項目履歴管理 等の有効化
```

> ⚠️ **誤解しやすい点**: API 参照名は **後から変更不可**。命名は慎重に（PascalCase or snake_case）。

### 2.3 外部オブジェクト

Salesforce 外部の DB を **Salesforce Connect** 経由でリアルタイム参照。**`__x`** が末尾につく。データは Salesforce 内に保存されない。

## 4. リレーション (Relationship) — 「行同士の関係」

### 4.1 リレーションの種類

| 種類 | 用途 | 削除挙動 | 積み上げ集計 |
|------|-----|--------|--------|
| **参照関係** | ゆるい参照 | 子残る (or エラー or null) | ❌ |
| **主従関係** | 強い親子 | 子も削除（カスケード） | ✅ |
| **外部参照関係** | 外部オブジェクト参照 | - | ❌ |
| **間接参照関係** | 外部オブジェクトから Salesforce へ | - | ❌ |
| **階層関係** | ユーザ → ユーザ専用（上司階層） | 子残る | ❌ |
| **多対多** | M:N（ジャンクションオブジェクト経由で主従関係2本） | 中間消える | ✅（ジャンクションで） |

### 4.2 多対多リレーション

<img src="https://d2f75plg0t6qwk.cloudfront.net/tech_article/sf-object-config-tech-jr/2604d33b-04.png" alt="4.2 多対多リレーション （フロー図 横）" width="1536" height="1024">

**実装:**
1. ジャンクションオブジェクト（受講登録）を作成
2. ジャンクションに **主従関係を2本** 張る（学生と講座それぞれ）
3. 1本目が主主従関係（共有・所有を支配）、2本目が副主従関係

### 4.3 参照関係の動作オプション

参照関係項目作成時に「親が削除された時の挙動」を選択:

| オプション | 動作 |
|---------|------|
| **値をクリア** (推奨) | 子の参照関係値を null に |
| **削除を許可しない** | 親削除を**拒否** |
| **このレコードを削除** | 子も削除（主従関係相当） |

## 8. 入力規則 (Validation Rule) — 「保存時の拒否」

### 8.1 構文の基本

**数式が `TRUE` のときエラーになる**（= エラー条件を書く）。

```
ルール名: Amount_Positive
数式:
  Amount__c <= 0
エラーメッセージ: 金額は0より大きい値を入力してください
エラー表示位置: 項目 (Amount__c) または ページの先頭
```

### 8.2 よく使うパターン

```
1. 必須化（条件付き）:
   AND(ISPICKVAL(Stage__c, "Closed Won"), ISBLANK(Close_Date__c))

2. 過去日禁止:
   Contract_Date__c < TODAY()

3. 特定 レコードタイプ の時だけチェック:
   AND(
     RecordType.DeveloperName = "Renew",
     ISBLANK(Previous_Contract__c)
   )

4. 金額と確度の整合:
   AND(
     ISPICKVAL(Stage__c, "Closed Won"),
     Probability__c <> 100
   )

5. メール形式チェック（内蔵だが業務固有）:
   NOT(REGEX(Email, "^[A-Za-z0-9._%+-]+@example\\.co\\.jp$"))
```

### 8.3 評価順序

```
1. システム検証（形式チェック、必須項目）
2. 保存前フロー / Apex トリガ (before)
3. カスタム入力規則
4. 重複ルール
5. DBコミット
6. 保存後フロー / Apex トリガ (after)
```

> ⚠️ **保存前フローで値補正したのに入力規則で蹴られた**、という事故は頻発。順序を理解する。

## 9. 数式項目 & 積み上げ集計項目

### 9.1 数式項目

```
項目名: Tax_Included_Amount__c
戻り値の型: 通貨
数式: Amount__c * 1.1
```

```
項目名: Days_Until_Close__c
戻り値の型: 数値
数式: Close_Date__c - TODAY()
```

```
項目名: Status_Label__c (別オブジェクト参照)
戻り値の型: テキスト
数式:
  CASE(
    Account.Industry,
    "Real Estate", "不動産",
    "Construction", "建設",
    "その他"
  )
```

> 💡 **別オブジェクト参照の数式**: `Account.Field__c` で親の値を参照可。最大 **10階層** まで遡れる。

### 9.2 積み上げ集計項目

```
親オブジェクト: Property__c
項目名: Total_Contract_Amount__c
型: 積み上げ集計
ソース: Contract__c (主従関係の子)
集計種別: SUM
集計項目: Amount__c
絞り込み: Stage__c = "Closed Won"
```

→ 親に「受注 の契約金額合計」が自動計算される。子レコード追加・削除・編集で**自動再計算**。

| 集計種別 | 説明 |
|----------|------|
| COUNT | 子レコード件数 |
| SUM | 数値項目の合計 |
| MIN / MAX | 最小・最大 |

> ⚠️ **制限**: 1オブジェクトあたり積み上げ集計項目は **最大25個**。再計算負荷を考慮。

## 10. 重複管理

### 10.1 構成要素

<img src="https://d2f75plg0t6qwk.cloudfront.net/tech_article/sf-object-config-tech-jr/c344344d-06.png" alt="10.1 構成要素 （フロー図 縦）" width="1536" height="1024">

### 10.2 一致ルール (Matching Rule)

「何をもって重複とするか」を定義:

```
オブジェクト: 取引先
一致条件 1: 名前 (完全一致、空白無視)
一致条件 2: 請求先郵便番号 (完全一致)
一致ロジック: 1 AND 2
```

### 10.3 重複ルール (Duplicate Rule)

「いつ・どう動くか」を定義:

```
オブジェクト: 取引先
条件:
  - ソース: 全ユーザ
  - 作成時のアクション: ブロック（拒否）
  - 編集時のアクション: 警告とともに許可
  - 一致ルール: 上で作ったルール
```

> 💡 **デフォルトで標準ルール**（標準取引先重複ルール など）が有効。カスタムで差し替え可。

## 12. データ保存順序（実行順序） — 試験頻出

```
1. システム検証（必須項目、データ型、最大長）
2. ★ 保存前フロー（レコードトリガー）
3. ★ Apex トリガ (before insert / before update)
4. ★ カスタム入力規則
5. 重複ルール
6. ★ DBコミット
7. ★ Apex トリガ (after insert / after update)
8. ★ 保存後フロー（レコードトリガー）
9. 割り当てルール（リード/ケース）
10. 自動応答ルール
11. ワークフロールール（廃止予定）
12. プロセスビルダー（廃止予定）
13. エスカレーションルール（ケース）
14. 積み上げ集計項目 再計算
15. グリッドビュー / リストビュー反映
16. レコードロック解除
17. コミット後ロジック（送信メール・アウトバウンドメッセージ）
```

> 💡 **保存前フローが最速**な理由: ステップ2で完結、DML が走らないため。値補正用途で使うべき。

## 13. よくあるハマりどころ (Jr.向けチートシート)

### ❌ ハマり1: 「項目を作ったのに画面に出ない」

- 原因: **ページレイアウトに追加していない**
- 対処: 設定 > オブジェクトマネージャ > 対象オブジェクト > ページレイアウトで対象レイアウトを編集、項目をドラッグ

### ❌ ハマり2: 「積み上げ集計項目が作れない」

- 原因: **参照関係しか張ってない（主従関係が必要）**
- 対処: 参照関係 → 主従関係 に変換（子レコードに親が全件入っている前提）

### ❌ ハマり3: 「主従関係に変換できない」

- 原因: 子レコードに **null の参照関係が1件でもある**
- 対処: 全子レコードの参照関係を埋める → 変換実行

### ❌ ハマり4: 「入力規則が動かない」

- 原因候補:
  1. **「有効化」チェックが OFF**
  2. 数式が `FALSE` を返す書き方になっている（エラー時に TRUE が正解）
  3. プロファイルの **システム権限に「入力規則のスキップ」が ON**
- 対処: 有効化、数式の反転、権限確認

### ❌ ハマり5: 「ページレイアウトに必須項目を追加したのに API インポートで弾かれない」

- 原因: **ページレイアウトの必須は UI のみ。API には効かない**
- 対処: 項目自体を必須にする or 入力規則で `ISBLANK()` チェック

### ❌ ハマり6: 「選択リストの選択肢を増やしたのにレコードタイプ別画面で出ない」

- 原因: **レコードタイプの選択リスト値で割り当てていない**
- 対処: 設定 > レコードタイプ > 編集 > 選択リスト値

### ❌ ハマり7: 「レコードトリガーフローが想定と違うタイミングで動く」

- 原因: **保存前 / 保存後 の選択ミス**
- 対処:
  - 値補正・同レコード書換 → 保存前
  - 関連レコード操作・メール → 保存後

### ❌ ハマり8: 「積み上げ集計項目の値が再計算されない」

- 原因: **手動 Apex 操作 / 大量データ更新の遅延**
- 対処: 設定 > オブジェクトマネージャ > 項目詳細 > "強制的な再計算"

### ❌ ハマり9: 「カスタムオブジェクトの API 参照名が長くて怒られる」

- 原因: API 参照名は **40文字以内**（`__c` 除く）
- 対処: 短く命名（`Property__c` not `RealEstatePropertyManagement__c`）

### ❌ ハマり10: 「項目の連動関係が表示されない」

- 原因: 制御項目と従属項目のページレイアウト配置順（制御項目が先になければならない）
- 対処: ページレイアウトで順序を入れ替え
