# /error-triage - エラートリアージコマンド

## 概要

Asana「CRMインシデント管理」プロジェクトの「未対応」セクションにあるエラータスクを**全件分析**し、緊急度に応じた深さで調査を行い、**各タスクのAsanaコメントに調査結果を投稿**するコマンド。

**目的:** エラー対応が必要かどうかの判別。緊急度が高いものはフル調査。
**実行頻度:** 毎日手動で実行

## 使用方法

```
# 標準実行（未対応セクションの全エラーを分析）
/error-triage

# 引数指定
/error-triage $ARGUMENTS
```

## 定数定義

### Asanaプロジェクト

```
PROJECT_GID = "1210141860554779"   # CRMインシデント管理
```

### セクションGID

```
未対応セクション（メイン分析対象）:
  "1210141860554780"   # 未対応

過去タスク照合用:
  "1212411628434999"   # 完了済み
  "1212411628435000"   # 過去のエラー
  "1212427130084717"   # 重複エラー
  "1212427130084716"   # 影響のないエラー
  "1213037757239679"   # SINGLE_EMAIL_LIMIT_EXCEEDED
```

### トリアージレベルと調査深度

```
🔴 要緊急 → フル調査（/investigate 相当）
  設計書確認 → ソースコード精査 → 過去類似チェック → 原因推定 → 対応提案

🟡 要対応 → 簡易調査
  エラー種別判定 → クラス名特定 → ソースコード該当箇所確認 → 過去類似チェック

🟢 様子見 → 最小分析
  エラー種別判定 → 過去類似チェック → 分類理由の記載
```

## トリアージ判定基準

### 🔴 要緊急（即座に対応が必要 → フル調査）

以下のいずれかに該当する場合:

| 条件                                     | 判定理由                           |
| ---------------------------------------- | ---------------------------------- |
| DmlException（INSERT/UPDATE失敗）        | データ不整合・レコード破損リスク   |
| NullPointerException が繰り返し発生      | システム障害の可能性               |
| REQUIRED_FIELD_MISSING                   | 必須項目の欠落（データ品質問題）   |
| タスク名に「緊急」「障害」「本番」を含む | 明示的な緊急マーク                 |
| 過去24時間以内に同一エラーが3回以上発生  | 連続障害の兆候                     |
| Callout系エラー（外部API連携断）         | 業務プロセス停止リスク             |
| UNABLE_TO_LOCK_ROW                       | レコードロック競合（並行処理問題） |

### 🟡 要対応（近日中に対応が必要 → 簡易調査）

以下のいずれかに該当する場合:

| 条件                                                   | 判定理由                   |
| ------------------------------------------------------ | -------------------------- |
| 初回発生のエラー（過去に類似なし）                     | 新規問題の可能性           |
| LimitException（ガバナ制限超過）                       | パフォーマンス問題         |
| Timeout / AsyncException                               | 非同期処理の問題           |
| 入力規則エラー（ValidationException）                  | 設定不備またはデータ不整合 |
| 過去に「重複エラー」に分類されたが内容が異なるパターン | 見落としの可能性           |

### 🟢 様子見（経過観察で問題なし → 最小分析）

以下のいずれかに該当する場合:

| 条件                                         | 判定理由                       |
| -------------------------------------------- | ------------------------------ |
| 過去に完了済みで同一エラーが解決済み         | 既知・解決済み                 |
| 過去に3回以上発生し毎回「重複エラー」に分類  | 既知の定常エラー               |
| SINGLE_EMAIL_LIMIT_EXCEEDED                  | メール送信上限（定常的に発生） |
| 一時的なエラー（リトライで解消するパターン） | 自己回復型                     |

**重要:** 判定基準はガイドラインです。AIがエラー内容を総合的に判断し、迷った場合は上位レベル（より緊急側）に判定してください。

## 実行フロー

```
Step 1: Asana APIで全タスク取得 → 「未対応」タスクをフィルタ
  ↓
Step 2: 過去タスクを抽出（類似判定・頻度カウント用）
  ↓
Step 3: 各タスクを簡易分析 → トリアージ判定（🔴/🟡/🟢）
  ↓
Step 4: 緊急度に応じた調査を実施
  ├─ 🔴 → フル調査（/investigate相当）
  ├─ 🟡 → 簡易調査
  └─ 🟢 → 最小分析
  ↓
Step 5: 各タスクのAsanaコメントに調査結果を投稿
  ↓
Step 6: コンソールにサマリーを表示
```

## Step 1: 全タスク取得

```
呼び出し:
  mcp__asana__asana_get_tasks({
    project: "1210141860554779",
    opt_fields: "name,notes,created_at,completed,memberships.section.gid,memberships.section.name,custom_fields.gid,custom_fields.name,custom_fields.enum_value.name",
    limit: 100
  })

ページネーション:
  - レスポンスに next_page.offset がある場合、offset を指定して次ページ取得
  - 全ページの data を結合

フィルタリング:
  未対応タスク = memberships に section.gid == "1210141860554780" を含む
  completed == true のタスクは除外
```

**0件の場合:** 「未対応エラー0件」とコンソールに表示して終了。

## Step 2: 過去タスクの抽出

Step 1 で取得済みの全タスクから過去タスクを抽出する（追加APIコール不要）。

```
照合用セクション:
  - "1212411628434999"   # 完了済み
  - "1212411628435000"   # 過去のエラー
  - "1212427130084717"   # 重複エラー
  - "1212427130084716"   # 影響のないエラー
  - "1213037757239679"   # SINGLE_EMAIL_LIMIT_EXCEEDED
```

## Step 3: トリアージ判定

各未対応タスクについて、タイトル（name）と説明文（notes）からエラー種別を判定し、過去タスクとの類似照合を行い、トリアージレベルを決定する。

### エラー種別判定パターン

```
- "DmlException" or "FIELD_CUSTOM_VALIDATION_EXCEPTION" → DML系
- "NullPointerException" → Null参照
- "LimitException" or "CPU time limit" or "SOQL" → ガバナ制限
- "CalloutException" or "Timeout" → 外部連携
- "UNABLE_TO_LOCK_ROW" → レコードロック
- "Flow" or "Interview" → フローエラー
- "REQUIRED_FIELD_MISSING" → 必須項目欠落
- "SINGLE_EMAIL_LIMIT" → メール上限
- "AsyncException" or "Queueable" or "Batch" → 非同期処理
- その他 → AI判断
```

### 類似エラー照合

```
1. タスク名から主要キーワードを抽出（クラス名、エラー種別）
2. 過去タスク名に同じキーワードが含まれるものをカウント
3. 直近7日間 / 直近30日間 の発生回数を算出
4. 過去の分類先セクション（完了済み/重複エラー/影響なし等）を確認
```

## Step 4: 緊急度に応じた調査

### 🔴 フル調査（/investigate 相当）

各🔴タスクに対して以下を実施:

#### 4a-1: クラス名・フロー名の抽出

```
抽出パターン:
  - タイトル先頭のPascalCase文字列 → Apexクラス名候補
  - "Trigger: [Name]" → トリガー名
  - "Flow: [Name]" or "Flow Interview: [Name]" → フロー名
  - ".cls" を含む文字列 → Apexクラス名
  - notes内のスタックトレースからクラス名を抽出
```

#### 4a-2: 設計書の確認

```
検索対象:
  doc/detailed-design/apex/    → Apex設計書
  doc/detailed-design/trigger/ → トリガー設計書
  doc/detailed-design/flow/    → フロー設計書
  doc/detailed-design/objects/ → オブジェクト定義書
  doc/domains/                 → 概要設計書

検索方法:
  - 抽出したクラス名・フロー名でファイル検索（Glob）
  - 関連オブジェクト名で検索
  - 見つかった設計書から仕様・意図を把握
```

#### 4a-3: ソースコードの精査

```
検索対象:
  force-app/main/default/classes/[クラス名].cls
  force-app/main/default/triggers/[トリガー名].trigger
  force-app/main/default/flows/[フロー名].flow-meta.xml

確認内容:
  - エラー行番号がある場合、該当行の前後10行を確認
  - try-catch の有無と例外処理の適切さ
  - DML操作の箇所とバルク処理対応
  - 外部連携（Callout）の箇所
  - 入力規則との干渉可能性（Salesforce実行順序を考慮）
  - 関連するトリガー・フローとの依存関係
```

#### 4a-4: 原因推定と対応提案

```
分析結果から:
  - エラーの根本原因を推定
  - 影響範囲を評価
  - 具体的な対応策を提案（コード修正/設定変更/データ修正等）
  - 優先度と推定工数の目安
```

### 🟡 簡易調査

各🟡タスクに対して以下を実施:

```
1. クラス名・フロー名の抽出（Step 4a-1 と同じ）
2. ソースコードの該当箇所確認（Grepで簡易検索）
   - エラー行番号がある場合、その前後5行のみ
   - try-catch の有無
   - 基本的なエラー箇所の特定
3. 過去の類似エラーとの比較
4. 簡易的な対応方針の記載
```

### 🟢 最小分析

各🟢タスクに対して以下を実施:

```
1. エラー種別の確認
2. 過去の同一エラーの発生回数と分類先
3. 様子見と判断した理由の記載
4. 注意すべき点があれば記載
```

## Step 5: Asanaコメント投稿

各タスクに調査結果をAsanaコメントとして投稿する。

### コメント投稿方法

AsanaのStories API（コメント追加）を使用する。

```
mcp__asana__asana_create_story_for_task({
  task_id: "[TASK_GID]",
  text: "[調査結果テキスト]"
})
```

**注意:** もし上記ツールが利用できない場合は、以下のcurlで代替する:

```bash
curl -X POST "https://app.asana.com/api/1.0/tasks/[TASK_GID]/stories" \
  -H "Authorization: Bearer {{ASANA_PERSONAL_ACCESS_TOKEN}}" \
  -H "Content-Type: application/json" \
  -d '{"data": {"text": "[調査結果テキスト]"}}'
```

### 🔴 要緊急のコメントフォーマット

```
🔴 エラートリアージ: 要緊急（自動分析 YYYY-MM-DD）

【エラー種別】DmlException
【関連コンポーネント】FormAutoSubmitQueue (Apex Class)
【発生頻度】直近7日: X回 / 直近30日: X回

■ 設計書確認
- 関連設計書: doc/detailed-design/apex/FormAutoSubmitQueue.md
- 仕様: MoveIn__c作成時に非同期でフォーム自動送信を実行

■ ソースコード分析
- エラー箇所: FormAutoSubmitQueue.cls:150 付近
- DML操作: MoveIn__c の insert（L.148-152）
- try-catch: なし → 例外が上位に伝搬
- 入力規則干渉: RecallCheck2 が ISCHANGED(Status__c) で発動する可能性あり

■ 原因推定
MoveIn__cのinsert時、RecallCheck2入力規則がStatus__c項目の
初期値に反応してDmlExceptionが発生している可能性が高い。
Salesforce実行順序: Before Trigger → Validation Rules の順で
トリガーによる項目変更が入力規則に引っかかるパターン。

■ 過去の類似エラー
- 2026-03-15: 同一エラーが「完了済み」にあり（対応済みだが再発の可能性）
- 2026-03-10: 「重複エラー」に分類

■ 対応提案
1. FormAutoSubmitQueue.cls:150 付近にtry-catchを追加
2. RecallCheck2入力規則の条件式を確認し、自動処理との干渉を解消
3. 推定工数: 2-3H

※ この分析はAIによる自動トリアージです。最終判断はエンジニアが行ってください。
```

### 🟡 要対応のコメントフォーマット

```
🟡 エラートリアージ: 要対応（自動分析 YYYY-MM-DD）

【エラー種別】LimitException
【関連コンポーネント】AccountBatchProcess (Apex Class)
【発生頻度】直近7日: X回 / 直近30日: X回

■ エラー箇所
- AccountBatchProcess.cls で CPU time limit exceeded
- L.85: SOQLクエリがループ内で実行されている可能性

■ 過去の類似エラー
- 初回発生（過去に類似なし）

■ 対応方針
- バッチサイズの見直しまたはSOQLの最適化が必要
- 詳細調査を推奨

※ AIによる自動トリアージです。
```

### 🟢 様子見のコメントフォーマット

```
🟢 エラートリアージ: 様子見（自動分析 YYYY-MM-DD）

【エラー種別】SINGLE_EMAIL_LIMIT_EXCEEDED
【発生頻度】直近7日: X回 / 直近30日: X回

■ 判定理由
メール送信上限による定常的なエラー。過去に15回発生し、
うち12回が「重複エラー」に分類されている。
業務影響は限定的。

■ 注意点
- 発生頻度が急増した場合は再評価が必要

※ AIによる自動トリアージです。
```

## エッジケース

| ケース                                   | 対応                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------- |
| 未対応0件                                | 「未対応エラー0件」とコンソール表示して終了                          |
| クラス名を抽出できない                   | 「関連コンポーネント: 不明」と記載。ソースコード確認はスキップ       |
| ソースコードが見つからない               | 「ソースコード未検出（外部システムまたは設定エラーの可能性）」と記載 |
| 設計書が見つからない                     | 「関連設計書: なし」と記載。ソースコードのみで分析                   |
| Asanaコメント投稿失敗                    | エラーを表示し、次のタスクに進む。最後に失敗件数を報告               |
| 未対応タスクが20件以上                   | 🔴のフル調査は実施するが、🟢は一括コメント（個別分析を省略）を検討   |
| 同一タスクに過去のトリアージコメントあり | 新しいコメントを追加する（上書きしない）                             |

## 実行時の注意

1. **全件取得**: ページネーションが終わるまで取得し続けること
2. **ソースコード確認は効率的に**: Glob/Grepで必要箇所のみ。全ファイル読み込み禁止
3. **コメント投稿順**: 🔴 → 🟡 → 🟢 の順で処理
4. **迷ったら上位判定**: トリアージレベルに迷った場合は、より緊急側に判定
5. **既存コメント確認不要**: 過去のトリアージコメントがあっても気にせず新規コメントを追加
