# /design - 設計フェーズ

## 概要

AIネイティブ開発フローのフェーズB「設計」を実行するコマンド。
要件定義書に基づき、設計書群とタスク分解を自動生成します。

## トリガー

- `/requirement` 完了後
- 要件定義書の承認後

## 使用方法

```
/design [Asana依頼名]
```

または

```
/design
# → doc_draft/requirement/ から最新の要件を自動検出
```

## 実行フロー

### B-0: 事前確認（Git認証）

**最初に必ず実行**: GitHub CLIの認証状態を確認

```bash
gh auth status
```

#### 認証済みの場合

```
✓ Logged in to github.com account {ユーザー名}
```

→ B-0.5へ進む

#### 未認証の場合

```
You are not logged into any GitHub hosts.
```

→ 以下のメッセージを表示し、認証を実行:

```
⚠️ GitHub CLIの認証が必要です。
PRを作成するためにGitHub認証を行います。

以下のコマンドを実行してください:
gh auth login

手順:
1. GitHub.com を選択
2. HTTPS を選択
3. Yes（Authenticate Git with your GitHub credentials）
4. Login with a web browser を選択
5. ブラウザで認証を完了
```

認証完了後、再度 `gh auth status` で確認してからB-0.5へ進む。

### B-0.5: 事前確認（要件定義書・Slack URL）

`/design` の最初に、要件定義の完了確認と必須項目のチェックを行う。

#### Step 1: 要件定義書の完了確認

`doc_draft/requirement/[依頼名]/requirement.md` が存在するか確認する。

- **存在する場合**: requirement.md を読み込み、Step 2 へ進む
- **存在しない場合**: 以下のメッセージを表示し、`/requirement` の実行を促す

```
⚠️ 要件定義書が見つかりません。
先に /requirement を実行して要件定義書を作成してください。

→ /requirement を実行しますか？（はい/いいえ）
```

「はい」の場合は `/requirement` フローに戻る。「いいえ」の場合は理由を確認し、要件定義なしで進めるか判断する。

#### Step 2: SlackスレッドURL の確認（必須）

Asana MCPでタスクの「【APP】SlackのスレッドURL - 1」フィールドを確認する。

**カスタムフィールドGID**: `1212822906463960`

- **URLが入力済みの場合**: Step 3 へ進む
- **URLが未入力の場合**: 以下のメッセージを表示し、登録を促す

```
⚠️ SlackのスレッドURLが未登録です（必須項目）。

AsanaタスクのカスタムフィールドにSlackスレッドURLを登録してください:
  フィールド名: 【APP】SlackのスレッドURL - 1

→ SlackのスレッドURLを入力してください:
```

エンジニアがURLを入力したら、Asana MCPで該当フィールドを更新する:

```
asana_update_task:
  task_id: {AsanaタスクID}
  custom_fields: {"1212822906463960": "{入力されたSlackURL}"}
```

> **注意**: SlackスレッドURLは必須です。未登録の場合は登録完了まで設計フェーズに進まないこと。

Step 2 完了後、B-1（設計開始）へ進む。

#### カスタムフィールドGID一覧

| フィールド名                  | GID                | タイプ | 用途                      |
| ----------------------------- | ------------------ | ------ | ------------------------- |
| 【APP】SlackのスレッドURL - 1 | `1212822906463960` | text   | Slackスレッド必須チェック |

### B-1: 設計開始

1. 要件定義書（requirement.md）を読み込み（B-0.5で取得済み）
2. 新規機能 or 追加機能かを判定
3. **Itandi連携判定**（自動）

#### Itandi連携の自動判定

要件定義書・設計対象の内容から、以下のキーワード・条件に該当する場合は **Itandi連携あり** と判定する:

| 判定条件                                                       | 例                                                    |
| -------------------------------------------------------------- | ----------------------------------------------------- |
| 要件定義書にItandi/イタンジ/いたんじへの言及がある             | 「イタンジBB連携」「Itandi CSV」等                    |
| 対象オブジェクト・項目にItandi関連のAPI名が含まれる            | `itandiPropSyncID__c`, `ItandiPreviewStartDate__c` 等 |
| Itandiとのデータ連携（CSV取込、API連携）に関する仕様変更がある | インポートバッチ、連携フロー等                        |
| Itandi側の仕様（BB、内見予約等）に影響する変更がある           | BB連携の制御変更等                                    |

**判定結果の記録**: 概要設計書（readme.md）に以下を記載する:

```markdown
## 外部連携影響

- **Itandi連携**: あり / なし
- **影響内容**: （ありの場合、どのような仕様変更があるかを記載）
- **documentリポジトリ更新**: 必要（`classlab-inc/document` の `Inside/Itandi/` 配下）
```

> **Itandi連携ありの場合**: B-4（タスク分解）で、documentリポジトリの仕様ドキュメント更新タスクが自動追加される。

### B-2: 設計書作成

#### 新規機能の場合

- `.ai/templates/` からテンプレートを使用して新規作成

#### 追加機能の場合

- 既存の設計書をコピーし、差分を修正

生成する設計書:

1. **概要設計書.md** - システム全体像、アーキテクチャ
2. **機能設計書.md** - 機能詳細、画面設計、API設計
3. **詳細設計書.md** - クラス設計、メソッド仕様

### B-2.5: 干渉チェック（自動実行・必須）

設計書が生成された後、設計内容と既存の自動化処理（入力規則・トリガー・フロー）の干渉を自動チェックする。

#### 手順

**Step 1: 設計書から対象情報を抽出**

B-2で生成した設計書（概要設計書・詳細設計書）を読み取り、以下を特定する:

| 抽出項目         | 抽出元                            | 例                               |
| ---------------- | --------------------------------- | -------------------------------- |
| 対象オブジェクト | 設計書内のオブジェクト参照        | `MoveIn__c`                      |
| 対象項目         | 設計書内の項目参照・更新項目      | `Satus__c`, `ReasonForReCall__c` |
| 操作種別         | 設計書内のDML操作・処理タイミング | `update`                         |

**Step 2: Pythonスクリプトを実行**

抽出した情報で干渉チェックスクリプトを実行する。**必ず実行すること（スキップ禁止）。**

```bash
python3 scripts/tools/impact-check.py \
  --object [対象オブジェクト] \
  --fields [対象項目をカンマ区切り] \
  --operation [操作種別] \
  --output json
```

対象オブジェクトが複数ある場合は、オブジェクトごとに実行する。

**Step 3: 結果を設計書に反映**

スクリプトの出力（JSON）を解釈し、概要設計書（`readme.md`）に「干渉チェック結果」セクションを追記する:

```markdown
## 干渉チェック結果

実行日: YYYY-MM-DD
対象: [オブジェクト名] / [項目名] / [操作種別]

### サマリー

| 自動化種別   | 総数 | Active | 干渉リスクあり |
| ------------ | ---- | ------ | -------------- |
| 入力規則     | X件  | X件    | X件            |
| Apexトリガー | X件  | X件    | X件            |
| フロー       | X件  | X件    | X件            |

### 高リスク項目

（HIGH リスクの項目を記載。なければ「なし」）

### 依頼者への確認事項

（確認が必要な事項を記載。なければ「なし」）

### 対策方針

（高リスク項目に対する設計上の対策を記載）
```

**Step 4: 高リスク項目への対応**

- **HIGH リスクが0件**: そのままB-3へ進む
- **HIGH リスクが1件以上**: エンジニアに高リスク項目を提示し、設計書に対策方針を追記してからB-3へ進む

#### 注意

- 設計書に記載されている**すべてのDML操作対象オブジェクト**に対してチェックを実行する
- 新規トリガー・フローを設計した場合、そのトリガー・フローが操作する対象オブジェクトもチェック対象に含める
- スクリプトの出力はそのまま貼るのではなく、AIが業務的な文脈を加えて要約する

### B-3: 担当エンジニア確認

担当エンジニアがローカルで設計書を確認・修正（干渉チェック結果含む）

### B-4: タスク分解

設計書に基づきタスクを自動分解

1. 設計書の内容からタスクを洗い出し
2. タスク一覧を生成（この時点では工数は空欄）
3. **レビュータスクを自動追加**（末尾に工数なしで追加）

```markdown
## タスク分解（工数未入力）

| #   | タスク           | 工数 |
| --- | ---------------- | ---- |
| 1   | API設計          |      |
| 2   | DB設計           |      |
| 3   | 実装: Controller |      |
| 4   | 実装: Service    |      |
| 5   | テストコード     |      |
| 6   | コードレビュー   |      |
```

#### レビュータスク自動追加ルール

タスク分解の末尾に、以下のレビュータスクを **自動追加** する。工数は空欄のままでよい。

| タスク名       | 工数 | 説明                                 |
| -------------- | ---- | ------------------------------------ |
| コードレビュー | -    | 実装後のコードレビュー（エンジニア） |

- エンジニアへの工数質問は不要
- Asanaサブタスクとして登録する際も予定時間なしで作成する

#### Itandi仕様ドキュメント更新タスク自動追加ルール

B-1でItandi連携ありと判定された場合、タスク分解に以下のタスクを **自動追加** する。
コードレビューの直前に追加し、工数はエンジニアが見積もりを入力する。

| タスク名                   | 工数               | 説明                                                                               |
| -------------------------- | ------------------ | ---------------------------------------------------------------------------------- |
| Itandi仕様ドキュメント更新 | （エンジニア入力） | `classlab-inc/document` リポジトリの `Inside/Itandi/` 配下の関連ドキュメントを更新 |

**タスク説明に含める内容**:

- 更新が必要と推定されるファイル（設計内容から判断: `api.md`, `batch.md`, `data.md`, `flow.md` 等）
- 変更の概要（どのような仕様追加・変更があるか）
- documentリポジトリのPR作成も含む

**タスク分解の例（Itandi連携ありの場合）**:

```markdown
## タスク分解（工数未入力）

| #   | タスク                     | 工数 |
| --- | -------------------------- | ---- |
| 1   | API設計                    |      |
| 2   | DB設計                     |      |
| 3   | 実装: Controller           |      |
| 4   | 実装: Service              |      |
| 5   | テストコード               |      |
| 6   | Itandi仕様ドキュメント更新 |      |
| 7   | コードレビュー             |      |
```

> **注意**: Itandi仕様ドキュメント更新タスクは工数入力対象（レビュータスクとは異なる）。B-4.5でエンジニアに見積もりを確認する。

タスク1: API設計

### B-5: 工数入力（Asana自動同期）

**B-4.5完了後、自動実行される**

#### Step 1: 親タスクに合計工数を設定

1. 合計工数を分単位に変換（例: 6.5H → 390分）
2. Asana MCPで親タスクの「予定時間（Estimated time）」に自動入力

```
asana_update_task:
  task_id: {親タスクID}
  custom_fields: {"1203561023086990": {合計工数（分）}}
```

#### Step 2: 分解したタスクをサブタスクとして登録

各タスクをAsanaのサブタスクとして作成する。工数ありのタスクは予定時間を設定、工数なし（`-`）のタスクは予定時間なしで作成。

**重要: Asanaではサブタスクが上から追加されるため、タスク一覧の逆順（末尾→先頭）で作成すること。**

```
# 逆順で作成する（例: タスク6 → タスク5 → ... → タスク1）

# 工数ありのタスク
asana_create_task:
  name: {タスク名}
  parent: {親タスクID}
  custom_fields: {"1203561023086990": {工数（分）}}

# 工数なしのタスク（コードレビュー等）
asana_create_task:
  name: {タスク名}
  parent: {親タスクID}
  # custom_fields の予定時間は設定しない
```
