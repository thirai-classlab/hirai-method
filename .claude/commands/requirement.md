# /requirement - 要件定義フェーズ

## 概要

AIネイティブ開発フローのフェーズA「要件定義」を実行するコマンド。
Asana・Slack・Gitから関連情報を収集し、要件定義書を自動生成します。

## トリガー

- 新規機能の要件定義開始時
- 追加機能の要件定義開始時
- Asanaタスクに基づく開発開始時

## 使用方法

```
/requirement [Asanaタスク名またはURL]
```

または

```
/requirement
# → 対話形式で情報を収集
```

## 実行フロー

### A-1: 初期確認

1. エンジニアに「新規機能」か「既存機能の編集」かを確認
2. 新規機能の場合、開発ドメインが新規かどうかを確認する（ビジネスドメイン知識の26ドメイン構成を参照）
3. Asanaタスク情報の特定

### A-1.5: ヒアリングシート確認

`doc_draft/requirement/[依頼名]/hearing.md` が存在するか確認する。

- **存在する場合**: hearing.md を読み込み、業務要件の素材として活用する。MCP取得情報と統合して要件定義書を生成する。
- **存在しない場合**: 対話形式で業務要件をヒアリングする（従来フロー）。

> **推奨**: `/hearing` コマンドで事前にヒアリングシートを作成しておくと、要件定義書の精度が向上します。

### A-2: 並列情報取得

以下の情報を並列で取得:

- **Asana MCP**: タスク詳細、関連タスク、コメント
- **Slack MCP**: 関連スレッド、議論履歴（※条件付き）
- **GitHub MCP**: 関連コード、既存実装
- **GitHub MCP（ビジネスドメイン知識）**: `classlab-inc/document` リポジトリから `Inside/Onboarding/03-business-domain.md` を取得し、業務フロー・主要オブジェクト・ドメイン構成等のビジネスコンテキストを要件定義に反映する

#### ビジネスドメイン知識の活用方法

`03-business-domain.md` から取得した以下の情報を、要件定義書の各セクションに反映する:

| 取得情報                       | 活用先                                                   |
| ------------------------------ | -------------------------------------------------------- |
| 業務フロー（NW→CX→EA）         | 「運用フロー（人の動き）」セクションの記述に活用         |
| 主要オブジェクト関連図         | 「インプットデータ」「処理概要」のオブジェクト特定に活用 |
| 自動化処理（トリガー・バッチ） | 「既存機能への影響」の評価に活用                         |
| 外部連携                       | 「制約事項」や「非機能要件」の検討に活用                 |
| 26ドメイン構成                 | 依頼がどのドメインに属するかの分類に活用                 |

> **取得方法**: GitHub MCPの `get_file_contents` を使用
>
> ```
> owner: classlab-inc
> repo: document
> path: Inside/Onboarding/03-business-domain.md
> ```

#### Slackメッセージ検索の条件

| トークン設定           | 検索機能    | 動作               |
| ---------------------- | ----------- | ------------------ |
| User Token（xoxp）あり | ✅ 利用可能 | 通常通り検索実行   |
| Bot Token（xoxb）のみ  | ❌ 利用不可 | **検索をスキップ** |

**注意**: Bot Tokenのみの場合、Slackのメッセージ検索はスキップされます。
スキップ時は以下のメッセージを表示:

```
⚠️ Slackメッセージ検索をスキップしました（User Tokenが未設定のため）
```

### A-3: ドキュメント生成

> **干渉チェックについて:** 詳細な干渉チェックは `/design` のB-2.5フェーズで自動実行されます。
> 設計書に対象オブジェクト・項目・操作が明記された段階でPythonスクリプトによる機械的走査を行います。

1. `doc_draft/requirement/[Asana依頼名]/` フォルダを作成
2. `requirement.md` を生成

### A-3.5: 非機能要件・インフラ管理チェック

要件定義書の生成時に、以下の技術要素が含まれるかをエンジニアに確認する。
該当する場合は、非機能要件セクションの該当欄にチェックを入れ、管理シートへの登録を促す。

| 確認項目                                             | 確認内容                                                |
| ---------------------------------------------------- | ------------------------------------------------------- |
| 架電番号（発信番号）マッピングの変更                 | ロジックツリーのスプレッドシートが更新済みか確認が必要  |
| GAS開発の有無                                        | GAS管理シートへの追加が必要か                           |
| オンプレミス（Windowsサーバー）の有無                | オンプレミス管理シートへの追加が必要か                  |
| 拡張機能開発の有無                                   | 拡張機能管理シートへの追加が必要か                      |
| 非同期処理（Batch/Queueable/Future/Scheduled）の有無 | DailyAsyncApexExecutions の日次予算確認・登録が必要か   |
| API実行（REST/SOAP/外部Callout）の有無               | DailyApiRequests の日次予算確認・登録が必要か           |
| サイト公開（Site/Experience Cloud/VFページ）の有無   | 公開範囲（一般公開/関係者のみ）と認証要件の定義が必要か |

#### 架電番号マッピングの検出と注意喚起

依頼内容（Asanaタスク名・説明・Slackスレッド等）に以下のキーワードが含まれる場合、**自動的に注意文言を表示**する：

**検出キーワード:** `架電番号`, `発信番号`, `架電マッピング`, `発信番号マッピング`, `CallNumber`, `MoveIn__c.CallNumber__c`

**表示する注意文言:**

```
⚠️ 架電番号（発信番号）マッピングの変更を伴う依頼を検出しました。

架電マッピングの編集を依頼する場合、必ず以下のスプレッドシートのロジックツリーを
先に変更してもらってから依頼を実施してください。

📋 ロジックツリー管理シート:
https://docs.google.com/spreadsheets/d/1g6KevIamymnZxcfATUMLlwMuoJPaZ_844h4qs5Ch5NQ/edit?gid=747706832#gid=747706832

→ ロジックツリーは更新済みですか？（はい/いいえ）
```

「いいえ」の場合は、ロジックツリーの更新を先に行うよう案内し、要件定義を一時中断する。

> **重要**: DailyAsyncApexExecutions / DailyApiRequests はorg全体で共有される上限であり、超過するとSalesforceが停止する可能性があります。該当する場合は必ず予算管理シートを確認してください。
