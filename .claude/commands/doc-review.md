# /doc-review - ドキュメント読み合わせ中のレビュー・修正コマンド

## 概要

ドキュメント読み合わせ中に不備や疑問を見つけた際、AIにサクッと伝えて即座に対応するコマンド。

**設計書:** `doc_draft/basic-design/ドキュメント読み合わせ運用/README.md`

## 使用方法

```
/doc-review [ドメイン名] [内容]
```

**引数:**

- `ドメイン名`: 読んでいるドメイン名（`doc/domains/` 配下のフォルダ名、部分一致OK）
- `内容`: 不備の説明、疑問、修正依頼などを自由記述

## 使用例

```
# 設計書の記述が実装と違う
/doc-review 自動申込 フロー図のStep3、実際のコードだとOCCTO APIの呼び出し順が逆になってる

# 仕様がわからない
/doc-review イタンジ連携 イタンジBBとイタンジの違いって何？どこで使い分けてる？

# 情報が古い
/doc-review 空室通電 MoveIn__c.Status__cの選択値が現在の本番と一致してない気がする

# 設計書に情報が足りない
/doc-review 従業員管理 スキルマスタとの連携部分の記載がない

# 誤字・表記ミス
/doc-review ZoomPhone Zoom Phone の API 名が間違ってる。ZoomPhoneLog__c じゃなくて ZoomCallLog__c
```

## 実行手順

### Step 1: ドメイン特定

引数の `ドメイン名` から対象ドメインを特定する。

1. `doc/domains/` 配下のフォルダ名と部分一致検索する
2. 一致するものが複数ある場合は AskUserQuestion で確認
3. 一致するものがない場合は `doc_draft/basic-design/` も検索
4. 対象ドメインの `README.md` を読み込む

### Step 2: 内容の分類

引数の `内容` を以下の3タイプに自動分類する:

| タイプ         | 判定基準                                             | アクション                                 |
| -------------- | ---------------------------------------------------- | ------------------------------------------ |
| **不備・修正** | 「間違い」「違う」「誤り」「古い」「更新」「修正」等 | 設計書を直接修正する                       |
| **疑問・質問** | 「わからない」「なぜ」「違いは」「どう」「?」等      | コードベース・メタデータを調査して回答する |
| **追記・補足** | 「足りない」「記載がない」「追加して」等             | 設計書に情報を追記する                     |

> 分類に迷う場合は AskUserQuestion で確認する。

### Step 3: タイプ別の処理

---

#### A. 不備・修正の場合

1. **現状確認**: 対象ドメインの設計書（README.md）の該当箇所を特定
2. **事実確認**: 以下のソースで正しい情報を確認
   - `force-app/main/default/` 配下のメタデータ（XML）
   - Apex クラス・トリガーのコード
   - `doc/detailed-design/objects/` のオブジェクト設計書
3. **修正実行**: 設計書を Edit ツールで直接修正
4. **差分表示**: 修正箇所を明確に表示

**出力フォーマット:**

```
## 修正完了

**ドメイン:** [ドメイン名]
**ファイル:** doc/domains/[ドメイン名]/README.md
**修正内容:**
- [修正前] → [修正後]

**確認元:** [確認に使用したファイル/メタデータのパス]
```

---

#### B. 疑問・質問の場合

1. **調査**: 以下のソースを並列で調査
   - 対象ドメインの設計書
   - 関連するオブジェクト設計書（`doc/detailed-design/objects/`）
   - メタデータ（`force-app/main/default/`）
   - Apex コード
   - 他のドメインの設計書（関連がある場合）
2. **回答**: 簡潔に回答する（長文にしない）
3. **参照先提示**: 詳細を知りたい場合の参照先を提示

**出力フォーマット:**

```
## 回答

**質問:** [元の質問]

[簡潔な回答（3-5行程度）]

**参照:**
- [関連ファイルパス1]
- [関連ファイルパス2]
```

---

#### C. 追記・補足の場合

1. **不足情報の収集**: メタデータ・コードから必要な情報を収集
2. **追記案の提示**: まず追記内容を表示して確認
3. **確認後に追記**: ユーザーの確認後、設計書に追記

**出力フォーマット:**

```
## 追記案

**ドメイン:** [ドメイン名]
**追記箇所:** [セクション名]
**追記内容:**

[追記する内容のプレビュー]

この内容で追記してよいですか？
```

---

### Step 4: ログ記録

実行結果を読み合わせログとして記録する:

**ログファイル:** `doc_draft/basic-design/ドキュメント読み合わせ運用/review-log.md`

追記フォーマット（ファイルが存在しない場合は新規作成）:

```
| [日付] | [ドメイン名] | [タイプ] | [概要（1行）] | [対応状況] |
```

## ルール

- **簡潔に対応する**: 読み合わせは30分しかない。長い調査が必要な場合は「後で `/investigate` で詳細調査」と伝えて概要だけ回答する
- **修正は直接行う**: 確認が取れた不備は即座に設計書を修正する。PRは後でまとめて作る
- **推測で修正しない**: メタデータやコードで事実確認できない場合は修正せず、確認事項として記録する
- **既存フォーマットを崩さない**: 設計書の既存の構成・スタイルを維持して修正・追記する
